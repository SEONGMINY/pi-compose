# Implementation Plan — Pi + Ghostty 재설계

- 기준: [PRD](PRD.md) · [Architecture](ARCHITECTURE.md) · [TRD](TRD.md)
- 상태: **새 방향 구현 전 계획**. 이전 tmux/workmux/Orca Phase 0–6 계획은 현행 작업 순서가 아닙니다.
- 원칙: 사용자 검증을 위해 기능 구현과 별도로 테스트/CI/PR 병합을 자동 실행하지 않습니다. 이전 구현 코드와 사용자 세션·Worktree는 보존합니다.

## 1. 구현 목표

**Main에서 설계·의사결정 → 선택한 Main을 정확히 Fork해 Work에서 개발 → 독립 Support 실행 → Work 결과 Summary 확인 → 사용자가 필요한 결정만 Main에 반영**하는 흐름을 Pi와 Ghostty만으로 사용할 수 있게 합니다.

기능을 얻기 위해 Pi 런타임·Extension·Git 관리자를 다시 만들지 않습니다. 재사용 기능과 실제 공백을 먼저 확인합니다.

## 2. 진행 순서 제안

| 단계 | 필요한 결과 | 구현 전 확인할 것 |
| --- | --- | --- |
| **P0. 기존 구현과 원본 보존** | 현재 Main/Work/Support 세션과 Git 자산 식별; Orca와 tmux/workmux 의존 제거 범위 확인 | 오래된 코드·세션·Worktree를 무단 삭제하지 않기 |
| **P1. Pi + Ghostty 기본 흐름** | 사용자가 선택한 Main을 고정 영역에 표시, 실행 중 Work/Support 분할 연결 | Ghostty 실제 Split/프로세스/종료 동작 |
| **P2. 정확한 Main Fork** | 최신 완료 Pi 지점 복제, 독립 Work 생성; Support 독립 대화 | Pi 세션 분기·Compaction·ContextEdit의 원본 정확성 |
| **P3. 종료·재접속** | Ghostty 종료 시 Agent 실행 종료; 명시적으로 Main 선택 후 Main만 재개 | 자식 프로세스·중복 실행·실패 복구의 실제 동작 |
| **P4. Work Summary Overlay** | 원래 Pi 터미널 위에 결과·**중요 결정 공유 후보 자동 표시**; 원본 화면 확인 | Pi TUI 이벤트와 Overlay, 완료/응답/실패 구분 |
| **P5. 프로젝트 문서 맥락** | 중요한 승인 결정 즉시 기존 docs 갱신; 사용자 요청 시만 선택적 문서 조회 | 짧은 지침의 누락 여부, 신규 문서 확인 및 충돌 판단 |
| **P6. 사용자 요청형 Handoff** | Main 자동 주입 금지. 사용자가 수신 Work를 지정하면 **`pi-intercom` + 작은 Compose Extension**으로 중요한 결정·WHY·출처 전송; **응답 중인 수신 Work는 현재 Pi 턴 종료 후 모델에 반영** | `pi-intercom` 1:1 라우팅/Outbox 활용, 진행 중 턴 `steer` 방지, 실제 Pi 턴 종료 이벤트와 지연 전달 보장, 큐/수신/실패 구분 검증 필요 |

위 순서는 기술 의존성을 정리한 **구현 후보 순서**입니다. 세부 API·화면 상태·자동화 범위를 정책처럼 확정한 것이 아닙니다. 실제로 독립적인 구현 작업은 필요한 범위에서 병렬 처리할 수 있습니다.

## 3. 반드시 지킬 경계

- 사용자 실행 선택 없이 Work/Support 자동 시작 금지.
- Fork를 요약 프롬프트/같은 세션 Resume로 위장 금지. Main 원본 변경 금지.
- Summary가 모델 컨텍스트에 자동 삽입되는 것 금지. **화면 표시와 정보 전달 분리**.
- 새 Work 생성 시 미전달 중요 결정 자동 경고·동기화 금지. Work 간 전달은 **사용자가 대상과 전송을 선택할 때만** 실행하며, 수신 Work가 응답 중이면 **현재 Pi 턴 종료 후** 모델에 반영. 기능 개발 완료를 별도로 판별하거나 대기하지 않음. `pi-intercom` 재사용 범위를 넘는 범용 메시지 시스템을 만들지 않음.
- 문서 자동 갱신은 사용자 승인과 중요한 기존 제약의 변경 여부에 근거. 새 문서 생성은 확인.
- Work의 문서 수정 범위, Work 간 **턴 종료 이벤트 연동·수신 확인·실패 처리 세부**는 미확정. 구현자가 임의로 선택하지 않음.
- Git 병합·Worktree 정리·사용자 파일/세션 삭제는 자동 실행하지 않음.

## 4. 완료 판단의 기준

1. Main/Work/Support의 원본 Pi 대화와 컨텍스트 분리가 정확함을 사용자가 확인할 수 있습니다.
2. Main은 계속 보이고 실제 Work/Support 실행 창과 Summary Overlay를 확인할 수 있습니다.
3. 사용자 명시적 세션 복귀·Agent 종료·기존 기록 보존이 의도대로 동작합니다.
4. Work에서 여러 번 개발·수정해도 Main에 긴 실행 로그가 자동 유입되지 않습니다.
5. Summary의 **중요 결정 후보**는 자동 표시되지만, Main 수신은 사용자 요청 없이 일어나지 않습니다.
6. 문서화로 새 문서·중복 계약·불필요한 사용자 승인 Gate가 무분별하게 늘지 않습니다.

이 문서 자체는 어떤 완료 기준도 충족했다는 뜻이 아닙니다. 실제 환경에서 확인되지 않은 결과를 성공으로 주장하지 않습니다.
