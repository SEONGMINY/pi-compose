# Usage — Pi Compose 사용 흐름

> **실행 위치:** 이 문서의 정책 동기화와 Work-owned Handoff는 [Draft PR #37](https://github.com/SEONGMINY/pi-compose/pull/37) 브랜치의 구현 목표입니다. 기존 PR #25·기본 main의 동작과 구별하며 실제 Pi/Ghostty E2E 검증이 필요합니다.


> **목표 UX와 코드 상태를 구분합니다.** 2026-11-10 Handoff 단순화 목표는 PR #25에 코드로 연결 중이지만 실사용 검증 전입니다. 기존 `ask_user`·`/compose inbox` 구현은 새 기본 실행 경로와 구분합니다.

## 1. 목표 UX에서 Main을 시작합니다 (main 코드와 다름)

```bash
cd /path/to/project
pic                # 새 Main
pic -r             # Pi 기본 세션 선택 후 재개
pic -c             # Pi의 최근 세션 재개; Main이라고 보장하지 않음
```

Main에서 요구사항·기존 제약·선택 이유를 논의합니다. Pi 세션의 과거 정책을 문서와 자동 동기화하거나 잘못된 컨텍스트를 임의 수정하지 않습니다.

## 2. Work 또는 Support를 시작합니다

| 입력 | 목적 |
| --- | --- |
| `>w 작업` | 현재 Pi 대화의 완료 분기를 Fork해 구현 |
| `>>w 작업` | Work Fork + 별도 Git Worktree |
| `>s 작업` | 맥락 상속 없는 독립 조사·검증 |
| `>>s 작업` | 독립 Support + 별도 Worktree |
| `>w @세션 작업` | 같은 프로젝트에서 지정한 Pi 세션을 Fork |
| `>r` | 기존 Work 목록에서 선택해 같은 Pi 세션을 Ghostty Split으로 재개 (Fork 안 함) |
| `>r @기존Work` | 세션 이름·작업 내용·ID로 검색해 정확한 기존 Work 재개 |

**기존 Work 복구 예시:** Main에서 `>r` → 저장된 Work 선택 → 원래 Pi 세션 ID·Fork 계보·작업 디렉터리를 그대로 사용합니다. `>r @`를 입력하면 동일 제품의 이전 Work가 자동완성 후보로 나옵니다. 이미 실행 중인 Work가 있으면 해당 터미널로 이동하고 중복 실행하지 않습니다. 실제 Pi 프로세스가 종료됐는지 확인할 수 없으면 사용자에게 재개 위험을 먼저 알립니다. `>w @세션`은 **재개가 아니라 새로운 Fork**입니다. 별도 Git Worktree로 생성된 Work는 원래 Worktree 경로에서 재개하고 Git 파일을 복사·병합하지 않습니다.

각 Agent는 Ghostty Native Split에서 작동하는 방향입니다. `>>`는 원본의 미커밋 변경을 복사하거나 자동 병합하지 않습니다. 실제 실행 성공은 사용자 Mac의 설치·권한·Pi 상태에 좌우됩니다.

## 3. Work에서 결과를 보냅니다 — 최신 목표 UX

1. Work에서 `<`를 입력합니다.
2. Handoff Brief에서 **중요한 결과·필수 이유/제약·검증 상태**를 읽고 필요한 항목을 선택합니다. `E`로 출처와 원문을 확인할 수 있습니다.
3. Enter로 Main에 **정확히 추가될 Brief**를 확인하고 한 번 승인합니다. 취소하면 Main에 전달되지 않습니다.

이 경로는 **Draft PR #25에 코드로 연결 중이며 아직 macOS/Ghostty 통합 검증 전**입니다. 현재 `main`에서 사용할 수 있는 기능이라고 간주하지 마세요.

## 4. Main에서 정책을 확정하면 Work에 어떻게 전파되나요?

1. Main에서 "B안으로 확정합니다"처럼 기존 제안을 명확히 승인합니다. 별도 정책 등록 명령은 기본 흐름에 없습니다.
2. Pi Compose가 기존 Main 분기의 제안 원문·실제 사용자 승인을 연결해 결정 변경을 기록합니다. 불명확한 승인이나 근거 없는 추측은 전파하지 않습니다.
3. 이미 실행 중인 Work는 해당 Main 정책의 변경을 다음 안전한 모델 실행 경계에서 확인합니다. 유휴 중이거나 종료됐더라도 Work 재개 시 놓친 변경을 조회합니다.
4. Work는 변경이 현재 작업에 영향을 주는지 판단하고 작업 범위 안에서 수정합니다. 작업 범위를 크게 바꾸어야 한다면 Main에 결정 요청이 필요합니다.
5. Work `<` 미리보기에서는 최신 결정 확인 여부·전달되지 않은 변경·검증 상태를 사용자가 확인한 뒤 정확한 본문을 승인합니다.

정책 알림 수신은 변경을 코드에 적용했다는 증거가 아닙니다. Pi/Git 파일 변경이나 새로운 정책 승인을 동기화 기능이 대신 수행하지 않습니다.

### Work에서 정책 상태를 확인하는 위치 (PR #37)

Pi 1.4.0의 `ctx.ui.setWidget(...,{ placement:'aboveEditor' })`로 **입력창 바로 위**에만 한 줄을 표시합니다. 모델·토큰·비용 등 기존 Footer는 그대로 유지하며, 과거 `setStatus`로 표시하던 정책 문구는 제거합니다.

| 상태 | 표시 | 의미 |
| --- | --- | --- |
| `pending` | `● Main 정책 1건 · 다음 응답에 전달` | 새로운 승인 결정의 변경분을 발견했지만, Work의 후속 응답은 아직 확인되지 않음 |
| `delivered` | `○ Main 정책 전달됨 · Work 검토 대기` | Pi 세션에 전달 기록이 남았지만 작업 반영·테스트 성공의 증명은 아님 |
| `checked` | 표시 없음 | 변경분을 전달하고 후속 Work 응답을 확인했음. 실제 코드 적용을 증명하지는 않음 |
| `unavailable` | `! Main 승인 후보 1건 미확정 · Main /compose policy` | 확정되지 않은 승인 후보는 Main에서만 원문 검토. Work의 `?p`는 이미 확정된 정책 변경만 검토 |
| `stop` | `■ Main 작업 중단 지시 · 후속 수정 실행 제한` | 명시적 전체 Work 중단 결정이 유효하여 다음 수정 도구 실행이 제한됨 |

상태를 사용자에게 직접 승인하도록 요구하는 버튼은 없습니다. 변경이 없으면 상태 위젯도 표시하지 않습니다. 긴 정책 제목은 넓은 Split에서만 함께 보여주고, 한글·이모지 너비를 고려해 좁은 Split에서는 한 줄로 잘라 표시합니다. 이전 세션으로 전환하거나 종료하면 오래된 표시가 남지 않아야 합니다.

**직접 확인할 테스트:** Main에서 새 결정을 확정하고 Work를 열면 입력창 위에 알림이 나타나며, 같은 정책을 읽고 응답한 후에는 정상 상태로 숨겨집니다. 다시 다른 Main의 새 결정을 받아도 서로 다른 Work의 알림이 섞이지 않아야 합니다. 알림 상태만으로 `auth-policy.md`나 로그인 코드를 수정했다고 간주하지 않습니다.


### Work에서 확정 정책을 즉시 확인할 때: `?p`

Main 정책은 별도 등록이나 Work 조작 없이 자동으로 동기화됩니다. Work의 다음 정상 모델 호출에서 변경분만 전달하며, `?p`는 이 과정을 강제하는 필수 승인 단계가 **아닙니다**.

- Work가 유휴 상태에서 `?p` 입력: **승인된 변경이 아직 검토되지 않은 경우에만** Work 모델이 기존 맥락에서 한 번 검토합니다. 원문·기록된 이유(WHY)·차이·현재 작업 영향을 설명하고 **코드 수정·터미널 명령·Handoff를 수행하지 않습니다**. 읽기 전용 도구 외 호출도 차단합니다.
- 변경이 없거나 이미 확인했다면: 모델 호출 없이 알림을 표시합니다.
- Main 스냅샷 최신성/소유자를 검증하지 못하면: Work가 임의로 정책을 승인하지 않고 원인을 안내합니다.
- `! Main 승인 후보 N건 미확정`은 **확정 정책 변경 알림과 다릅니다**. 해당 사용자 발화의 진위 판정은 Main의 `/compose policy`에서만 가능합니다. 잘못 감지된 일반 대화를 반복 확인하게 만드는 근본 문제는 별도 승인 감지 정확도 검증 대상으로 남깁니다.

**객체의 자율성과 협력 원칙:** Main은 승인 정책·이유·범위의 권위자이며, Work는 전달된 정책의 해석·현재 작업 영향·검토 및 구현 결과를 소유합니다. Work `<`에서 사용자가 승인한 Handoff Brief만 Main이 수신하며, Main은 정상 경로에서 Work 내부 구현의 의미를 재심사하지 않습니다.

## 4.1 Main의 Handoff 자동 수신

Main은 Work에서 승인한 본문을 영속 보관하고 대상·원본 계보·활성 분기·해시·중복을 확인합니다. 정상 보고라면 **Main의 모델로 내용을 다시 심사하지 않고** 동일한 Work 참고 보고를 기록합니다. 모델 턴·정책 자동 변경·Git Merge는 수행하지 않습니다.

Main이 오프라인이면 원본을 보관하고 재개 후 처리합니다. 대상 분기와 원본 Work 계보가 다르면 자동 삽입하지 않고 `<`에서 예외로 확인할 수 있습니다.

- [PR #37](https://github.com/SEONGMINY/pi-compose/pull/37): 승인된 Main 정책 변경 전파와 Work-owned Handoff 수신 책임 변경이 작성된 후속 Draft입니다.
- 정상 Main 수신 경로에서 기존 Work Claim 비교 모델·추가 승인 경로를 사용하지 않습니다.
- Work의 자동 정책 전파는 임의의 사용자를 대신해 결정을 만드는 기능이 아닙니다. 승인된 원문을 식별하지 못하면 전파하지 않습니다.
- 최신 Draft 구현은 `npm run check` 및 실제 macOS/Pi/Ghostty 환경 검증을 통과하기 전까지 완료로 간주하지 않습니다.

## 6. 새 목표의 확인 시나리오

Main에서 관련 옵션을 논의 → 사용자가 B안 확정 → Work는 기존 Pi Fork 유지 → 변경분 수신 및 작업 영향 검토 → Work `<`에서 최신성·결과·WHY 확인 후 정확한 Brief 승인 → Main은 동일 Brief를 참고 보고로 자동 기록. 기존 결정·원본 세션·Git 작업 공간을 임의 수정하지 않는지 확인합니다.

## 7. PR #37 실사용 검증 (아직 수행하지 않음)

1. `pic` 새 Main과 실제 Fork `>w`/`>>w`가 각각 올바른 세션·작업 공간에서 시작되는지 확인
2. Main에서 2개 설계 대안을 제시하고 `B안으로 확정합니다` 입력 후 실제 승인 근거가 기록됐는지 확인
3. Work가 실행 중이면 다음 안전한 모델 호출에서 변경분만 받으며, Work 재개 후에도 놓친 변경이 다시 확인되는지 검증
4. 무관한 변경, 명시적 중단, 불완전한 승인, 여러 Main, 기존 분기로 되돌리기를 각각 재현
5. Work `<` 최종 Brief에 정확한 최신성 상태·미검증 테스트·WHY가 포함되는지 확인
6. Main에서 자동 내용 재심사·추가 모델 턴 없이 동일 승인 Brief가 기록되는지 Pi receipt로 확인
7. 두 번째 Work, Main 오프라인, Work→Work Fork, 같은 Handoff 재전송에서 중복·오경로 주입이 없는지 확인
8. 전체 추가 모델 호출/토큰/지연과 누락 변경으로 인한 재작업을 계측

실험 시 요구사항별 결과는 [정책 동기화 검증 상태 JSON](validation/policy-sync-20261111.json)과 감사 기록에 남깁니다. 테스트를 실행하지 않았다면 PASS라고 표시하지 않습니다.
