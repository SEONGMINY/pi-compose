# 사용 흐름 — 목표 경험과 현재 상태

[← README](../README.md) · [확정 정책](PRD.md)

> **Ghostty 중심 Overview 경험은 아직 미구현입니다.** 아래 흐름 대부분은 목표 UX이며, Draft PR #15의 임시 Pi 명령 `/compose handoff`·`/compose messages`·`/compose surfaces`는 코드가 작성됐지만 실제 실행 검증 전입니다. 오래된 tmux/workmux CLI는 이전 구현입니다.

## 1. Main에서 설계를 논의합니다

Main에서는 서비스의 목적·사용자 흐름·도메인 정책·API·데이터 구조·아키텍처·금지 조건·선택 이유를 논의합니다. 어떤 결정을 명확히 승인했다면 기존 관련 `docs/*` 문서에 즉시 반영하는 방향입니다. 새 문서가 필요하면 사용자에게 먼저 확인합니다.

Main의 맥락이 불충분할 때는 사용자가 명시적으로 요청해 `AGENTS.md`의 안내에서 관련 문서만 선택적으로 읽습니다. 이 명령/Skill의 이름은 아직 정해지지 않았습니다.

## 2. 필요할 때만 Work나 Support를 만듭니다

- **Work:** 실제 Main의 활성 완료 Pi 대화 지점을 Fork해 구현하거나 테스트 코드를 작성합니다. Main과 Work는 별도 대화입니다.
- **Support:** 맥락이 불필요한 코드 탐색, 웹 조사, 테스트 실행·검증 등에 사용합니다.
- 실행 공간은 현재 디렉터리 또는 별도 Git Worktree로 작업에 맞게 선택합니다. Fork와 Worktree는 서로 다른 개념입니다.
- Agent를 생성·실행할지 사용자가 명시적으로 결정합니다. Main이 임의로 개발 작업을 시작하지 않습니다.

예: Main에서 복약 정책을 결정하고 Work에서 알림 기능을 개발합니다. 테스트 코드는 그 이유를 아는 Work에서 작성할 수 있고, 별도 Support가 실행 결과를 확인해 오류를 Work에 보고할 수 있습니다.

## 3. 프로덕트·Agent·메시지를 탐색합니다

**`pic`을 실행한 화면에서만** Pi Compose 사이드바가 나타납니다. 그 안에서는 **프로덕트별 보기**와 **전체 Agent 보기**를 오갈 수 있어야 합니다. 프로덕트는 `Pillo`, `Pi Compose`처럼 하나의 제품 또는 프로젝트이며, 그 아래 여러 Main이 있습니다. Main은 화면에서 `Main · 복약관리`가 아니라 **`복약관리`**로 표시합니다. 관계와 역할은 이름을 생략해도 유지됩니다.

`pic` 화면에서 Main·Work·Support 또는 내부 작업 화면을 바꿔도 사이드바는 유지합니다. **일반 Ghostty 탭으로 이동하면 Pi Compose 사이드바는 나타나지 않고**, 다시 `pic` 탭으로 돌아오면 기존 관리 화면을 확인합니다. 이는 Ghostty의 모든 탭에 항상 고정되는 전역 사이드바가 아닙니다.

**메시지 관리는 사이드바의 별도 기능**입니다. Work A의 Summary에 표시된 공유 후보와 실제 다른 Agent에 전송한 메시지를 구분해, 메시지 내역과 대기/수신/실패 등 알아야 할 상태를 확인할 수 있어야 합니다. 정확한 목록 구성·필터·재시도 UI는 아직 결정하지 않았습니다.

## 4. 실행 중인 작업을 확인합니다

Ghostty에서 Main은 계속 보이고, **실행 중인 Work/Support는 각각 독립적인 Ghostty Split을 유지**합니다. 사이드바에서 Agent를 선택하면 해당 Agent의 **기존 Split으로 포커스를 이동**합니다. 선택하지 않은 Agent도 계속 실행되며, Split을 닫고 프로세스만 남겨 두거나 선택한 Agent만 같은 위치에 자동 교체 표시하지 않습니다. Agent가 많으면 화면이 비좁을 수 있습니다.

Work의 작업 결과/중요 결정 **공유 후보는 Summary Overlay에 자동 표시**합니다. 사용자가 선택하면 원래 Pi 대화 화면을 확인할 수 있어야 합니다. 표시할 상세 필드·완료 판정·재열기 UX는 아직 논의 중입니다.

## 5. 다른 Agent에 전달할 때는 사용자가 선택합니다

Work의 중요한 발견이나 승인 결정이 있어도 Main에는 자동 전송되지 않습니다. 사용자가 Main 반영을 요청하면 해당 내용의 **결정·이유·영향 범위·원본 근거**를 전달합니다. 긴 실행 로그와 전체 Diff는 Work/Support에 둡니다.

**다른 Work에 전달할 때도 자동 전송하지 않습니다.** Work A의 Summary에서 공유 후보를 확인한 사용자가 **받을 Work B와 전송을 명시적으로 선택**합니다. 전달에는 기존 `pi-intercom`과 이를 연결하는 작은 Pi Compose Extension을 사용하기로 했습니다. Work B가 현재 Pi 응답을 생성 중이라면 **그 턴이 종료된 뒤** 모델에 메시지가 반영되도록 합니다. **기능 개발 전체 완료를 기다리는 것은 아닙니다.** 실제 턴 종료 감지, 대기 상태 표시, 수신 확인·실패 UX는 아직 설계·검증이 필요합니다.

새 Work를 Fork할 때 이전 Work의 미반영 결정을 자동 경고하거나 동기화하지 않습니다. 문서를 다시 읽는 경우도 **현재 작업 공간에 있는 문서만** 알 수 있으며, 다른 Worktree에서 아직 통합하지 않은 결정은 자동으로 공유되지 않습니다.

### 현재 Draft 구현: `/compose handoff` · `/compose messages` · `/compose surfaces`

Pi TUI에서 사용자가 이 명령을 입력하면 연결된 수신 세션, 현재 Pi 활성 분기의 메시지, 전송 유형을 선택한 뒤 전달 문구를 검토·편집해 pi-intercom Outbox로 전송을 요청하도록 작성돼 있습니다. **실제 사용·설치·타입 검증 전**이며, pi-intercom이 없거나 수신 세션이 없으면 발송하지 않습니다. 이 과정에서 공유는 승인과 구분되고, `sent` 결과를 모델 읽음으로 표시하지 않습니다. `/compose messages`는 같은 Pi 세션의 기록에 남은 발송 요청·Outbox 결과·수신 intercom 메시지를 읽기 전용으로 보여줍니다. 결과가 확인되지 않은 요청은 `outcome-unknown`이며 모델 처리·승인 완료를 표시하지 않습니다. `/compose surfaces`는 Ghostty가 실제로 보유한 Terminal UUID·제목·cwd를 사용자에게 표시하고 선택한 **기존 Terminal**에 포커스하도록 작성했습니다. 이것은 Agent 목록이 아니며, cwd/제목에서 Pi 세션과 Agent 역할을 추측하지 않습니다. Ghostty Split을 만드는 API는 작성됐지만 아직 Agent 실행 경로에는 연결되지 않았습니다. 또한 새 세션 ID와 출처를 명시적으로 기록하는 Launch Ticket Hook, 정확한 완료 분기의 Native Work Fork 함수는 코드만 준비된 상태입니다. 이 함수들이 실제 `>w`/`>s`/`>>w`/`>>s` 사용자 입력과 Ghostty Split 실행까지 연결된 것은 아닙니다. Summary·Sidebar 및 프로덕트 소속 제한은 아직 없습니다.

## 6. 종료하고 다시 실행합니다

종료를 요청하면 **백그라운드로 유지(최소화/숨김)**하거나 **실행 중인 Agent를 종료**할지 선택할 수 있어야 합니다. 백그라운드를 선택하면 **Ghostty를 종료하지 않고 살아 있는 상태로 유지**하므로 Agent 작업이 계속 진행됩니다. 종료를 선택하면 프로세스를 중지하지만 저장된 Pi 대화와 Git 파일은 유지합니다. Ghostty 앱을 완전히 종료한 후에도 Agent가 별도 프로세스로 남는 구조는 제공하지 않습니다. 창 닫기·Cmd+Q 이벤트와 선택 UI의 연동은 아직 검증 대상입니다.

**백그라운드 유지 후 다시 화면으로 돌아오는 경우**에는 중단·재생성이 아니라 기존 실행 중인 Agent 화면으로 복귀합니다. **완전히 종료한 뒤 다음 실행**에서 사용자가 **특정 Main 세션을 선택**하면 Main만 재개합니다. 관련 Work/Support는 자동 실행하지 않습니다. 중단된 외부 명령도 자동 재실행하지 않습니다. 오래된 대화 기록이나 문서 파일을 되돌리는 행동은 사용자가 별도로 수행합니다.

## 7. 현재 구현과의 차이

새로운 Ghostty 분할/세션 제어·**프로덕트/Agent 및 메시지 관리 사이드바·종료 선택 UX**·Summary Overlay·선택적 문서 맥락 로드·전체 Handoff 경험은 아직 제품으로 완성되지 않았습니다. Draft PR #15는 Handoff 전송 경로의 일부 코드만 추가합니다. 이 저장소의 이전 CLI/설치 스크립트를 새 방향의 실행 방법으로 사용하지 마세요. 개발 순서와 남은 기술 검증은 [Implementation Plan](IMPLEMENTATION_PLAN.md)과 [TRD](TRD.md)에서 확인할 수 있습니다.
