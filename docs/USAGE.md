# Pi Compose 사용 흐름

[← README](../README.md) · [제품 정책](PRD.md)

> 이 문서는 2026-11-09 확정된 Sidebar 제거·Main 직접 실행 정책을 설명합니다. 해당 변경은 작업 브랜치의 코드이며 macOS Ghostty 실사용 검증을 거치기 전입니다. 이전 Overview / Summary Overlay 경로는 현재 목표 UX가 아닙니다.

## 1. Main 시작과 복구

```bash
cd /path/to/project
pic                  # 새 Main 세션을 현재 터미널에서 시작
pic -r               # Pi의 기존 세션 선택 창
pic -c               # 이 디렉터리에서 가장 최근 Pi 세션 계속
pic --session <ID>    # 특정 Pi 세션
```

- bare `pic`은 매번 신규 Main이며, 저장된 세션을 자동 선택하거나 Overview를 열지 않습니다.
- Pi 자체 `/resume`, `/new` 기능은 계속 사용할 수 있습니다.
- `-c`는 최근 세션을 재개할 뿐 Main 우선 선택이 아닙니다. 저장된 Work/Support는 역할을 유지합니다.
- 신규 Main의 프로젝트 신원은 정규화된 작업 디렉터리의 안정적인 해시로 정합니다. 같은 디렉터리에서 새 Main을 만들어도 세션 ID는 매번 다릅니다.
- 같은 Pi 세션을 두 프로세스에서 중복 재개하는 동작을 자동 방지한다고 보장하지 않습니다. 이미 실행 중인 세션이라면 해당 터미널로 돌아가세요.

## 2. 실제 개발 작업 위임

Pi TUI의 **입력 첫머리**에 다음 명령을 사용합니다.

| 입력 | 동작 |
|---|---|
| `>w 작업` | 현재 Pi 활성 완료 분기를 Fork한 Work 생성 |
| `>>w 작업` | Work Fork + 현재 Git HEAD 기준 새 Worktree 생성 |
| `>s 작업` | 맥락을 상속하지 않는 독립 Support 생성 |
| `>>s 작업` | Support + 별도 Git Worktree |
| `>w @세션ID 작업` | 같은 제품/프로젝트의 저장된 특정 Pi 세션을 찾아 Fork |

- 호출한 Pi가 있는 **현재 Ghostty Terminal을 확인하고 그 오른쪽으로 Split**합니다. 더는 Sidebar UUID가 필요하지 않습니다.
- Work Fork의 원본 대화 트리와 활성 완료 분기를 확인합니다. Work 로그는 Main 대화에 자동으로 복사하지 않습니다.
- Support는 독립 세션입니다. 컨텍스트가 필요한 작업을 Support에 임의로 보내지 않습니다.
- 새 Split 영수증은 Ghostty가 표면을 만들었다는 뜻이지 Pi가 시작됐거나 업무를 완료했다는 확인이 아닙니다.
- `>>`의 새 Worktree는 원본 미커밋 변경을 복사하지 않습니다. 작업 종료 시 Git 브랜치 병합·삭제도 자동 수행하지 않습니다.
- Agent 생성은 사용자 입력에 의해서만 시작합니다. 모델이 자동으로 생성하거나 병렬화하지 않습니다.

## 3. Work 완료 후 자동 후보 준비·나중에 검토

```text
Work 독립 개발 (사용자는 다른 일에 집중)
  └─ Work가 과제 완료를 명시적으로 보고하고 Pi run 정리
       └─ Pi Compose가 완료 보고 여부 평가 (모델 호출 1회)
            ├─ 완료로 판단되지 않음: Handoff 완료 표시·자동 질문 없음
            └─ 완료 보고 + 확인 가능한 원문 근거
                 ├─ 공유 후보 1~5개를 Work 세션에 저장
                 ├─ 알림만 표시, 다른 Agent 포커스 이동 없음
                 └─ ask_user 활성화 시 Work에서 후보 선택 질문을 자동 요청
                      └─ 사용자는 나중에 돌아와 선택·자유 입력·추가 의견
                           └─ Work 모델은 선택 내용을 검토용 초안으로 정리
                                └─ Pi 에디터에서 본문 편집·최종 전송 확인 (추가 < 불필요)
```

**한 번의 Pi 응답 종료는 작업 완료와 다릅니다.** 완료를 명시한 Work 보고를 별도 모델로 평가해 후보를 생성하지만, 실제 구현·테스트·승인을 독립적으로 증명하는 것은 아닙니다. 질문 대기 중에도 다른 Agent의 작업은 계속 진행할 수 있습니다.

- 동일한 Work 실행 중 반복 요청은 중복 예약하지 않습니다.
- 실행 중단·오류로 완료된 Assistant 보고가 없다면 대기 요청을 폐기하며 성공으로 표시하지 않습니다.
- 요청 이후 새로운 Work 실행을 시작하거나 분기가 바뀌면, 오래된 기록을 다른 실행 결과로 오인하지 않도록 요청을 재확인합니다.
- 대기 요청은 현재 Pi 프로세스 메모리에만 존재합니다. 프로세스를 종료·재시작하면 복구되는 기능은 아닙니다.
- 완료 공유 후보는 사용자가 검토하지 않아도 **자동 준비·비컨텍스트 저장**합니다. 단, 선택·수정 및 Main 전송은 사용자가 검토할 때까지 기다립니다.
- `ask_user`가 없거나 준비가 실패해도 Work 기록은 유지합니다. 모델 비용·완료 오분류·툴 연결은 실제 환경 검증 대상입니다.
- `/compose review`로 저장된 후보의 질문을 다시 열 수 있습니다. 질문이 켜진 동안 다른 도구가 자동 송신하지 않게 합니다. 선택 후 자동으로 이어지는 편집·전송 확인 단계에서 취소할 수 있습니다. `<`는 자동 후보 흐름과 별개의 수동 전송 방법입니다.
- `<<`에는 기능을 부여하지 않습니다.

## 4. Handoff 근거와 Main 보호

기존 Compose Handoff는 완료된 Work 답변, 최근 사용자 지시, 일부 도구 출력에서 원문을 발췌해 Pi Entry ID와 함께 전달합니다. 인용문이 원본에 존재하는지 검사합니다.

- 원본 문구가 존재한다는 사실만으로 승인 주체·부정문·검증 범위가 정확히 해석됐다고 보장하지 않습니다.
- `테스트 코드 존재`와 `테스트 실행 완료`, `Work의 제안`과 `사용자의 승인`은 별개입니다.
- Main이 받는 메시지는 검토 자료입니다. 사용자 승인 없는 정책 변경이나 자동 개발 명령이 아닙니다.
- `/compose handoff`는 기존 수동 Handoff 경로, `/compose messages`는 기록 확인 경로입니다.
- `pi-intercom`이 없는 경우, 수신 대상 신원이 확인되지 않는 경우, 원본 출처가 바뀐 경우 전송하지 않습니다.
- 보호형 Work→Main Handoff의 로컬 저장 성공, Main의 명시적 D/I 요청, 실제 모델 처리, 정책 채택은 서로 다른 증거입니다. 일반 Outbox 메시지로 Main의 대화에 자동 주입하지 않습니다.

### 자동 질문이 열리지 않을 때

먼저 **해당 Work 터미널**에서 `/compose handoff-status`를 실행합니다. 표시되는 `Role`(Work 인식), `Ask User tool active`, `Saved candidates`, `Assessment`를 확인할 수 있습니다. 개인 정보나 대화 원문을 출력하지 않는 짧은 진단입니다.

이미 완료된 작업은 `/compose review`로 **후보 생성을 재시도**할 수 있으며, 코드를 새로 구현하거나 Work를 다시 시작할 필요가 없습니다. 사용자 승인 없이 Main에 전송하지 않습니다.

1. `pi list`에서 `pi-ask-user`가 설치됐는지 확인합니다. 없다면 사용자 승인 아래 `pi install npm:pi-ask-user@0.17.2`로 설치합니다.
2. 실행 중이던 Work는 `/reload`로 새 Extension 구성을 읽거나 새 Work에서 재현합니다.
3. Work가 **명시적으로 과제 완료를 보고하지 않았거나** 완료 분류/근거 추출에 실패하면 질문은 자동 생성되지 않습니다. 단순히 Pi 응답이 종료된 것만으로 완료 표시하지 않습니다.
4. 후보가 준비되었지만 질문이 취소됐거나 도구가 비활성이라면 `/compose review`로 다시 열 수 있습니다.
5. **일반 Work 완료 메시지에 `<`를 요구하는 것은 구버전 동작입니다.** `<`는 별도의 수동 Handoff 요청에만 사용합니다.
6. `Assessment`가 `not-complete`라면 모델이 완료로 분류하지 않았다는 의미이며, `failed`이면 제공자/JSON/스키마/원문 검증 등 실패 원인 코드가 함께 표시됩니다. `prepared`인데 질문이 없으면 `Ask User tool active`와 재검토 동작을 우선 확인합니다.

## 5. 레퍼런스 재사용과 미구현 사항

- [Pi 1.4.0](https://github.com/earendil-works/pi): 세션·Fork·기본 TUI/Resume·`input` / `agent_settled` 이벤트
- [pi-intercom 0.18.1](https://github.com/nicobailon/pi-intercom/tree/v0.18.1): 메시지 전달 및 Handover의 로딩·취소·편집 레퍼런스
- [pi-ask-user](https://github.com/edlsh/pi-ask-user): 사용자 질문·선택·자유 입력 레퍼런스

**현재 구현 상태:** `ask_user`를 독립 `streamSimple()`에서 직접 호출하지 않고 Work의 실제 모델 턴으로 연결하는 코드가 작성됐습니다. 기본 원본 UI의 다중 선택·자유 입력·추가 의견을 사용합니다. **macOS 실제 Pi 1.4.0에서 자동 질문·답변·검토 결과 저장·복구까지 성공했는지는 미검증**입니다.

## 6. 직접 실사용 확인할 항목

1. macOS Ghostty에서 `pic` 실행 시 Sidebar가 없고 Main이 현 터미널에서 시작되는지
2. 새로운 Main의 응답 완료 후 `>w`/ `>s`가 같은 Ghostty Tab에서 별도 Split을 만드는지
3. `pic -r`로 Work를 복구하면 역할과 원래 Fork 관계가 유지되는지
4. Work 실행 중 `<`를 제출해도 Work가 Steering·중단되지 않는지
5. Work가 종료돼도 Main으로 자동 전송되지 않고, 사용자 검토·승인을 거쳐서만 전송되는지
6. Work 중단·세션 변경·수신 Main 오프라인 상태에서 안전하게 전송을 막는지

코드 반영과 실사용 검증은 별도로 기록합니다. 실사용 테스트 결과가 없다면 검증 완료라고 표현하지 않습니다.


## Main 보호형 Work Handoff (P1–P5 개발 브랜치)

이 절의 기능은 `feat/pic-direct-main-handoff-20261109`에서 구현 중이며, 실제 macOS/Pi/Ghostty E2E 성공을 주장하지 않습니다.

### Work에서

1. `>w ...`로 **실제 Pi Fork** Work를 만듭니다.
2. Work가 작업 완료를 보고하면 기존처럼 `ask_user`가 공유 후보를 표시합니다.
3. **[HC1] 같은 고정 ID**를 가진 후보를 선택합니다. 선택된 항목과 원문 출처 ID만 전달 범위에 포함하며, 제목만으로 근거를 확정하지 않습니다.
4. Work가 Fork 당시의 맥락 및 Work 기록에서 필요한 조건/WHY/범위를 검색합니다. **현재 Main은 조회하지 않습니다.**
5. 최종 내용 미리보기에서 `O`는 원본 근거, `R`은 보완 요청(근거 검색 재시도), `S`는 **현재 표시한 본문 그대로 승인 후 보관**, Esc는 보류입니다. R은 검증되지 않은 주장 추가를 허용하지 않습니다.
6. 승인된 Handoff는 `~/.pi/compose/handoff-inbox-v1/`에 대상 Main 세션 ID별로 안전하게 저장됩니다. 선택 시 일반 intercom 대화 메시지를 사용하지 않으므로 Main 모델이 자동 실행되지 않습니다. Extension Channel은 선택적인 **알림**만 전달합니다.

### Main에서

- 수신 보관은 **모델 호출/대화 주입 없이** 진행됩니다. Main 창에 보관함 상태가 표시되거나 재개 시 자동 검색됩니다.
- `/compose inbox` → 검토할 Handoff 선택 → Main **현재 활성 분기**를 읽어 그때만 읽기 전용 모델 비교를 실행합니다.
- 결과는 항목별 `new`(확정이 아닌 신규 가능성), `duplicate`, `conflict`, `insufficient`로 표현하며 Main 원문 근거 ID를 제공합니다.
- `O`: Work 근거, `D`: 사용자가 명시적으로 Main 대화에서 논의, `I`: 비교상 *신규 가능성*이 있는 보고만 Main 맥락에 기록(정책 승인 아님), `C`: 중복으로 정리, `A`: 보관, Esc: 나중에. D·I의 모델 턴은 실행·파일 도구가 비활성화됩니다. 기존 결정은 자동 승인·변경되지 않습니다.
- 비교 도중/검토 후 Main 활성 분기가 바뀌면 예전 결과로 행동할 수 없고 다시 열어야 합니다.

### 안전 및 복구

- Work **후보 선택은 전송 승인도, Work 보고의 사실 보증도 아닙니다.**
- Main 수신 자체는 사용자 지시가 아니라 비컨텍스트 보관입니다. 받은 보고가 현재 Main 사용자 결정을 덮어쓰지 않습니다.
- 인용문은 실제 Work 분기 Entry에 존재해야 합니다. 원문 문자열 일치가 *의미적 정확성*까지 증명하는 것은 아닙니다.
- 보관함은 로컬 같은 사용자 계정에 한정하며 원격/다중 장치 동기화를 지원한다고 주장하지 않습니다.
- Extension Channel 연결 실패 시 본문은 로컬 보관됩니다. 수신 Main은 재개 후 `/compose inbox`로 읽을 수 있습니다. 수신 Main의 미실행/종료 자체가 전송 실패는 아닙니다.
- Work가 파일 보관 직후 종료돼 세션 수락 기록이 없으면 동일한 검토 ID·선택·수신자를 사용해 저장본을 복구합니다. Main에 중복 패키지를 만들지 않습니다.
- 별도 모델이 최종 전달문의 부정문·상태·WHY 등을 검토합니다. 중요한 의미 오류, 검색 누락 또는 검사 실패 시 원본 근거 보완 후 재검토해야 하며 S 전송이 차단됩니다.
- 공유 후보 생성 실패는 `/compose handoff-status`로 확인하고 `/compose review`로 다시 시도합니다.
- 근거 검색 실패 또는 비결정적인 의미 평가가 있으면 사용자에게 알려야 하며, 테스트 성공이나 정책 승인을 추측해서는 안 됩니다.


### 최종 Handoff의 품질 검사 기록

전송 미리보기에는 전달문을 검사한 모델의 ID와 검사 결과를 나타내는 메타데이터가 표시됩니다. 실제 저장된 패키지의 `qualityReview.checkedBodyHash`는 `finalMessageHash`와 일치해야 합니다. 이는 모델이 해당 본문을 의미 검토했다는 기록이며, Work 결과의 실제 테스트 통과·정책 승인·전달문 의미 정확성에 대한 보증은 아닙니다.
