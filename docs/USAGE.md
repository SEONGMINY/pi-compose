# Usage — Pi Compose 사용 흐름

> **현재 `main` 사용 주의:** 이 페이지의 `pic` 새 Main·`>w`/ `>s` 직접 위임·Work `<` → Main 알림 흐름은 목표 사용자 경험입니다. 현재 `main`의 `pic` 기본 실행은 Overview를 열며, 이전 구현 코드는 [PR #25](https://github.com/SEONGMINY/pi-compose/pull/25)에서 별도로 검증 중입니다. 실제 사용 가능 여부를 최신 목표와 혼동하지 마세요.


> **목표 UX와 코드 상태를 구분합니다.** 2026-11-10 Handoff 단순화 목표는 PR #25에 코드로 연결 중이지만 실사용 검증 전입니다. 기존 `ask_user`·`/compose inbox` 구현은 새 기본 실행 경로와 구분합니다.

## 1. 목표 UX에서 Main을 시작합니다 (main 코드와 다름)

```bash
cd /path/to/project
pic                # 새 Main
pic -r             # Pi 기본 세션 선택 후 재개
pic -c             # Pi의 최근 세션 재개; Main이라고 보장하지 않음
```

Main에서 요구사항·기존 제약·선택 이유를 논의합니다. Pi 세션의 과거 정책을 문서와 자동 동기화하거나 잘못된 컨텍스트를 임의 수정하지 않습니다.

## 2. Work 또는 Support를 시작합니다

| 입력 | 목적 |
| --- | --- |
| `>w 작업` | 현재 Pi 대화의 완료 분기를 Fork해 구현 |
| `>>w 작업` | Work Fork + 별도 Git Worktree |
| `>s 작업` | 맥락 상속 없는 독립 조사·검증 |
| `>>s 작업` | 독립 Support + 별도 Worktree |
| `>w @세션 작업` | 같은 프로젝트에서 지정한 Pi 세션을 Fork |

각 Agent는 Ghostty Native Split에서 작동하는 방향입니다. `>>`는 원본의 미커밋 변경을 복사하거나 자동 병합하지 않습니다. 실제 실행 성공은 사용자 Mac의 설치·권한·Pi 상태에 좌우됩니다.

## 3. Work에서 결과를 보냅니다 — 최신 목표 UX

1. Work에서 `<`를 입력합니다.
2. Handoff Brief에서 **중요한 결과·필수 이유/제약·검증 상태**를 읽고 필요한 항목을 선택합니다. `E`로 출처와 원문을 확인할 수 있습니다.
3. Enter로 Main에 **정확히 추가될 Brief**를 확인하고 한 번 승인합니다. 취소하면 Main에 전달되지 않습니다.

이 경로는 **Draft PR #25에 코드로 연결 중이며 아직 macOS/Ghostty 통합 검증 전**입니다. 현재 `main`에서 사용할 수 있는 기능이라고 간주하지 마세요.

## 4. Main에서 결과를 받습니다 — 최신 목표 UX

Main은 승인된 Brief를 영속 보관한 뒤, **해당 Main 활성 Fork 분기·최신 정책·중복·근거**를 검사합니다. 문제없으면 Work에서 승인한 동일 본문을 **Work 참고 보고**로 기록합니다. 별도 Main 수락은 필요하지 않으며 모델 턴도 자동 실행하지 않습니다. 이는 정책 승인이 아닙니다.

Main이 오프라인이면 같은 세션을 재개했을 때 다시 확인합니다. 충돌·불확실·다른 분기·비교 실패라면 Main의 `<`를 통해서만 **예외 검토**합니다. Pi 기록 확인 전에는 반영 완료로 판단하지 않습니다.

## 5. 현재 PR #25에서 이미 작성된 코드의 범위

- 이전 자동 후보·`ask_user` 코드는 기록과 테스트를 위해 남아 있지만, `extensions/compose.ts`의 최신 기본 경로에는 연결하지 않습니다.
- 원문 근거 확인 및 검토용 패키지 생성·로컬 저장
- Main의 `/compose inbox` 수동 검토·비교·참고 정보 반영
- 단위·정적 검사와 실제 macOS/Pi/Ghostty E2E 검증은 별개의 상태

위는 최신 UX로 확정된 사용법이 아닙니다. 실제 그 브랜치를 검증할 때만 [Handoff 구현 감사](HANDOFF_IMPLEMENTATION_AUDIT.md)를 참고합니다.

## 6. 확인할 실제 성공 조건

`pic` 신규 Main → `>w` 실제 완료 분기 Fork → Work에서 Brief 한 번 승인 → Main 안전 검사 후 동일 Work 참고 보고만 기록(충돌 시 예외 보류), 그동안 원본 Pi 기록과 기존 승인 정책이 보존되는지 확인합니다.

## 7. PR #25 Context Review 실사용 검증 시나리오

1. **정확한 브랜치**: `feat/pic-direct-main-handoff-20261109` 최신 커밋으로 로컬 작업 트리를 동기화합니다. Main 브랜치의 CLI와 혼동하지 않습니다.
2. **Main 실행**: 테스트 프로젝트에서 `node /path/to/pi-compose/bin/pic.mjs`를 실행합니다. Main에서 중요한 금지 조건과 WHY를 먼저 기록합니다.
3. **Work 위임**: Main 입력창에 `>w README를 개선하되 기존 내용은 삭제하지 마세요`를 입력합니다. Split이 열린 후 Work에서 작업·보고를 완료합니다.
4. **발신**: Work에서 `<` 입력. Handoff Brief가 선택할 결과·필수 WHY·검증 상태를 먼저 보여주는지 확인합니다. `↑↓` 후보 이동, `Space` 선택, `E`/`Tab` 근거, `N` 의견/근거 보완, `Enter` 실제 Main Brief 미리보기, 다시 `Enter` 전송 승인, `Esc` 취소. 미리보기에서 `Tab`은 Main에는 전송되지 않는 감사용 상세 원문을 보여줍니다.
5. **Main 자동 처리**: 동일 Main의 활성 Fork 분기에서 새 보고가 있고 충돌이 없다면, Main에서 `<`를 누르지 않아도 승인한 동일 Brief가 **모델 턴 없이** 참고 보고로 기록되는지 확인합니다.
6. **예외 수신**: 최신 Main 결정 충돌·불충분한 원문·다른 분기에서는 자동 반영하지 않고 보류합니다. Main의 `<`로 해당 결과를 확인·처리할 수 있는지 확인합니다.
7. **실패 검증**: Work의 불완료 보고, 모델 JSON 실패, 미실행 테스트, 강한 부정문, 오래된 WHY, Main 최신 승인 충돌, 중복·세션 재개를 확인합니다. 실행/결과를 확인하지 않았다면 성공이라고 기록하지 않습니다.


**실사용 수정 (2026-11-10 영상):** Work에서 `<`를 입력하면 후보 생성 전에 `1/3 Main 확인`, `2/3 후보 구성`, `3/3 필수 WHY/근거 확인` 상태가 지속 표시됩니다. Context Review는 숨겨진 목록·상세 포커스 모드를 제거하고, 공개 TUI에 없는 포커스 조회 대신 다이얼로그가 열린 동안 알려진 단축키를 입력 리스너에서 한 번 처리·소비하고 종료 시 리스너를 해제합니다. 이 변경은 아직 사용자 Ghostty 환경에서 재검증해야 합니다.
