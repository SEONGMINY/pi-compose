# PRD — Pi Compose

- 최신 합의: **2026-10-31**
- 상태: **제품 정책 합의 / 새로운 Ghostty 중심 구현·실사용 검증 전**
- 제품: Pi 기반의 조합 가능한 Coding Agent Harness

## 1. 해결하려는 문제

Main에서는 서비스 개발에 필요한 **고품질 맥락**을 쌓습니다. 문제와 목적, 도메인 스토리텔링과 사용자 흐름, 요구사항과 완료 조건, API·데이터 계약, 아키텍처, 제약, 고려한 대안, 결정의 결과 **및 이유**, 아직 결정되지 않은 사항 등이 포함됩니다.

여기서 고품질은 정보가 많다는 뜻이 아니라 **다음 판단을 올바르게 할 수 있도록 사실·결정·제안·불확실성이 정확히 구분되고 중요한 이유가 보존된 상태**를 뜻합니다. 잘못된 답변이 들어간 경우 사용자는 Pi 대화 트리의 이전 지점으로 돌아가 올바른 분기에서 논의를 계속할 수 있습니다.

긴 개발·탐색·오류·테스트·Diff 기록을 Main에 쌓으면 컨텍스트를 소모합니다. 반대로 새로운 Agent에게 짧은 요약만 주면 '왜 금지했는가', '절대 금지'의 강도, 거절한 대안이 사라질 수 있습니다.

**목표:** Main의 맥락을 지키면서 실제 구현과 독립 실행을 분리하고, 다중 작업의 상태·결과는 쉽게 파악하되 불필요한 정보를 Main 모델에 자동 전달하지 않습니다.

## 2. Agent 역할과 컨텍스트

| 구분 | 책임 | 컨텍스트 |
| --- | --- | --- |
| **Main** | 기획·요구사항·도메인·설계·중요 결정·다음 판단 | 실제 원본 Pi 대화. 여러 Main 가능 |
| **Work** | 맥락을 알아야 하는 개발·테스트 코드 작성·반복 수정 | **현재 Agent 또는 같은 프로덕트에서 명시적으로 선택한 Pi 세션**의 활성 분기 마지막 완료 지점을 실제 별도 Pi 세션으로 Fork |
| **Support** | 코드 탐색, 웹 조사, 테스트 **실행**, 독립 검증 | Main/Work 전체 대화를 상속하지 않는 독립 Pi 세션 |

- Fork는 **짧은 요약 전달이나 Resume로 대체하지 않습니다**. **선택한 모든 Pi 원본 세션의 JSONL을 변경하지 않으며**, 실제 Fork 시점과 출처를 검증합니다.
- **Main·Work·Support 어느 Pi 입력창에서든** 사용자가 명시적으로 요청하면 새 Work/Support를 실행할 수 있습니다. Agent 역할에 따른 생성·중첩 제한이나 임의의 깊이 제한을 두지 않습니다. **사용자 직접 위임**과 **Agent가 스스로 다른 Agent를 생성하는 자율 위임**은 별개이며, 자율 위임 권한은 후속 정책 결정 대상입니다. 임의의 자동 작업 스케줄링은 도입하지 않습니다.
- **Fork 원본 Pi 컨텍스트, 새 Agent를 요청한 세션, 실제 파일 작업 디렉터리**는 서로 다른 개념입니다. Fork/Independent 선택과 Shared Directory/Git Worktree 선택을 분리하고, 누가 누구를 생성했는지와 어떤 세션을 Fork했는지 별도로 보존합니다. 순차/병렬 여부는 작업에 따라 결정하며 Pi Extension의 사용 자유도를 유지합니다.
- 예: 기능 의도를 알아야 하는 테스트 **작성**은 Work에 맡기고, 테스트 **실행**은 Support에서 처리할 수 있습니다. 오류 로그를 받은 후 원래 맥락을 가진 Work에서 수정합니다.

### 프로덕트와 Main 관계

- **프로덕트**는 `Pillo`, `Pi Compose`처럼 하나의 프로젝트 또는 제품을 의미하며, 그 아래 **여러 Main**을 둘 수 있습니다. Main마다 관련 Work/Support 작업을 탐색할 수 있어야 합니다.
- 사용자는 **프로덕트 단위 보기와 전체 Agent 단위 보기**를 전환할 수 있어야 합니다. 실제 관계와 작업을 유지한 채 보이는 기준만 달라집니다.
- 사이드바의 Main 항목은 `Main · 복약관리` 대신 **`복약관리`처럼 이름만 표시**합니다. 내부 역할과 연결 관계는 유지하며, Work·Support 등 유형 구분이 필요하면 구조/상태로 식별합니다.

### 위임 입력의 제품 정책 (2026-10-31 확정)
- 기본 Pi 입력창에서 **단축어 + 자연어**와 **일반 자연어로 Agent에게 위임 요청**하는 두 경로를 제공합니다. 명시적 위임은 **Main·Work·Support 어느 입력창에서도 가능**하며, 단축어는 입력 **첫머리**에서만 해석합니다. 일반 문장에 있는 `>`나 기존 Pi 문법은 침범하지 않습니다. **Compose 전용 키보드 단축키를 추가하거나 Pi/Ghostty 키 바인딩을 변경하지 않습니다.**
- **명령어와 기본 Workspace는 다음과 같이 고정**하며, 이전 선택을 기억하지 않고 Workspace 선택창도 추가하지 않습니다.

  | 직접 위임 | Agent의 컨텍스트 | 파일 작업 공간 |
  | --- | --- | --- |
  | `>w 작업 지시` | 현재 Pi 세션의 완료 지점 Fork | **명령어를 입력한 Agent의 현재 디렉터리 공유** |
  | `>w @세션 작업 지시` | 선택한 같은 프로덕트 세션 Fork | 명령어를 입력한 Agent의 현재 디렉터리 공유 |
  | `>>w 작업 지시` | 현재 Pi 세션의 완료 지점 Fork | **새 Git Worktree** |
  | `>>w @세션 작업 지시` | 선택한 같은 프로덕트 세션 Fork | **새 Git Worktree** |
  | `>s 작업 지시` | **독립 Pi 세션**, Fork 없음 | 명령어를 입력한 Agent의 현재 디렉터리 공유 |
  | `>>s 작업 지시` | **독립 Pi 세션**, Fork 없음 | **새 Git Worktree** |

- `>w`/`>>w`에서 원본을 지정하지 않으면 **명령을 입력한 현재 Agent**를 Fork합니다. 현재 세션이 Support라도 명시적으로 요청한 Work의 Fork 원본이 될 수 있습니다. `>s`/`>>s`는 독립 Support이므로 Fork 원본 선택 `@세션`을 사용하지 않습니다. **다른 프로덕트의 세션은 Fork 검색·선택 대상에서 제외**합니다.
- 네 가지 직접 위임 명령은 **입력한 Agent의 모델을 호출하거나 그 대화에 요청을 남기지 않고** 처리합니다. **단축어와 선택용 `@세션` 토큰을 제외한 사용자의 작업 지시 원문**을 새 Agent의 최초 지시로 전송하고 생성과 함께 실행을 시작합니다. Work의 컨텍스트는 **선택한 원본 Pi 세션을 실제 Fork**하며 모델이 재작성한 요약으로 대체하지 않습니다.
- 일반 자연어 위임은 **입력한 Agent의 모델**이 읽고 판단하므로 그 위임 요청이 해당 Agent 대화에 남는 것을 허용합니다. 명시적 실행 의도·Fork 원본·Workspace 등 필수 정보가 분명하면 반복 확인 없이 실행하고, 모호한 요청을 임의로 자동 실행하지 않습니다. **모델의 자율적 다단계 재위임 허용 범위는 별도 결정 전까지 확정하지 않습니다.**
- `>w`/`>s`/`>>w`/`>>s` 뒤에 작업 지시가 없으면 즉시 Agent를 실행하지 않습니다. 입력 중인 텍스트는 취소·실패 시 가능한 한 보존합니다. Overview의 `+ Agent`는 지시 없이 Agent를 만드는 별도 진입점으로 허용합니다.
- **`>w @` / `>>w @` 세션 자동완성**은 **현재 프로덕트**의 Main·Work·Support 중 **실행 중이거나 종료되어 기록이 남은 Pi 세션**을 검색합니다. 세션 **이름 + 최근 실제 작업을 설명하는 한 줄 + 작업 디렉터리/Worktree 정보**를 표시하고, 이름·최근 작업 내용으로 검색합니다. 실제 선택값은 표시 이름이 아닌 **고유 Pi 세션 ID**로 식별합니다. 작업 설명은 기존 Summary 등 근거 있는 정보를 재사용하며 입력마다 LLM을 호출하지 않습니다. 의미 있는 Summary가 없다면 확인 가능한 최근 작업 지시를 표시합니다. 일반 `@` 파일 검색은 그대로 유지합니다.
- **`>`는 현재 디렉터리 공유**, **`>>`는 새 Git Worktree 생성**을 의미합니다. `@세션`으로 **Fork 대화**를 바꾸어도 **파일 작업 공간은 명령을 입력한 현재 Agent 기준**으로 결정합니다. 새 Worktree는 **명령 입력 Agent의 현재 브랜치 HEAD**를 시작점으로 별도 브랜치/체크아웃을 만들고, 원본 브랜치·디렉터리는 변경하지 않습니다. 미커밋 변경은 복사하지 않으며, 변경 사항이 있다면 그 사실을 알리되 매번 확인·커밋을 강제하지 않습니다. Git Merge·Worktree 자동 삭제도 하지 않습니다.

## 3. 실행 환경·세션·화면

- **Pi + Ghostty 단독 사용**. 이전 Orca 통합은 폐기하고 tmux/workmux를 새 제품에 사용하지 않습니다. 별도 GUI는 지금 개발하지 않습니다.
- **사이드바의 표시 범위는 `pic` Overview 화면으로 한정**합니다. `pic` 실행 시 Overview에 사이드바가 나타나며, 프로덕트·Agent·메시지 관리를 전환해도 유지합니다. 별도 Ghostty 작업 Tab에는 사이드바를 표시하지 않습니다. `pic` Overview Tab으로 복귀하면 사이드바와 그 위치에 남아 있는 실제 Pi TUI Split들을 다시 볼 수 있어야 합니다. 실제 터미널 영역 구성과 상태 유지 방식은 기술 검증 대상입니다.
- **Overview를 기본 진입 화면으로 사용하고 여러 Agent의 실제 Pi TUI를 Ghostty Split으로 함께 표시**합니다. 실행 중인 Agent는 각자의 고유 Ghostty 터미널(Surface)과 Pi 프로세스를 유지합니다. 화면 전환 때문에 Agent를 복제·재실행·Resume하지 않습니다.
- **Herdr·iTerm2의 이동(Move) UX 방향을 채택**합니다(2026-10-30 사용자 승인). 사용자가 특정 Agent를 별도 작업 Tab으로 이동하면 그 Agent의 **기존 터미널 자체가 위치를 변경**하고, Overview의 실제 Split 영역에서는 빠집니다. 사이드바의 Agent 목록·관계·상태는 유지하며 현재 위치로 탐색할 수 있어야 합니다. 사용자는 Overview로 돌아와 다른 Agent를 보거나 해당 Agent의 실제 터미널을 다시 Overview에 배치할 수 있어야 합니다. **한 Agent의 동일 Pi TUI를 여러 Tab에 동시 미러링하는 기능은 범위에서 제외**합니다.
- **Main도 Work·Support와 동일하게 Tab 간 이동할 수 있습니다**(2026-10-30 사용자 B안 승인). Main은 Overview에 고정하지 않습니다. Main을 이동하면 실제 Main Pi TUI는 해당 Tab에서만 표시되며, Overview 사이드바의 Main 항목·관계·상태는 유지합니다. Main의 Pi 세션·컨텍스트·Fork 원칙은 화면 위치와 독립적으로 유지합니다. **Overview 관리 TUI의 유지와 Main의 Split 고정은 다른 문제**이며, Main이 이동했다는 이유로 Overview 사이드바를 닫거나 Main을 새로 실행하지 않습니다.
- **기존 Split/Surface를 이동해도 Pi 프로세스와 세션 연속성을 보존**하는 것이 핵심 완료 조건입니다. 기존 화면을 닫고 새 Pi 프로세스를 Resume하여 이동을 흉내 내지 않습니다. 사이드바는 기존 정책대로 `pic` Overview 화면에서만 표시하며 일반 Ghostty Tab 전체에 주입하지 않습니다. Herdr App·herdr-core·별도 멀티플렉서/상주 프로세스 관리 계층은 도입하지 않습니다.
- **첫 번째 사용 가능한 버전의 Tab 이동 방식은 Ghostty 기본 드래그(A안)**로 확정합니다(2026-10-30 사용자 승인). 사용자가 기존 Surface를 직접 다른 Tab의 터미널 영역으로 이동하고, Overview로 돌아올 때도 직접 드래그합니다. 이 과정에서 **실제 Pi 프로세스·세션·Surface를 보존**하며, 이동을 위해 새 Pi를 실행하거나 Resume하지 않습니다. **메뉴 클릭 한 번으로 자동 이동하는 UX는 후속 과제**로 분리하고 현재 구현 범위에 포함하지 않습니다. Ghostty 기본 드래그의 실제 왕복 이동·동일 Surface 식별·대상 Tab 준비 및 실패 시 동작은 macOS 실사용 검증 대상입니다. 새 Agent는 생성 순서에 따라 마지막으로 추가된 Agent 옆에 이어 붙이며, 배치는 이후 사용자가 관리합니다. 정확한 Ghostty Split 생성 위치와 화면 공간 부족 시 동작은 기술 검증 대상입니다.
- **Summary Overlay는 필수입니다.** 원래 Pi TUI를 종료·복제·재개하지 않고 **같은 Agent의 터미널 화면 위에 겹쳐 보여줍니다**. 토글이나 별도 'Pi TUI 열기' 버튼 없이, 해당 Agent에 **포커스하면 즉시 Overlay를 해제**합니다. 아래 상태·표시 정책을 따릅니다. 실제 Ghostty/Pi 위 표시 방식은 미검증입니다.
- **독립된 사이드바 메시지 관리 기능도 필수입니다.** Summary에 흩어진 전달 내역을 각 Work 화면을 열지 않고 확인·관리할 수 있어야 합니다. 공유 후보와 실제 발송 메시지는 구분하며, 전송 대기·수신 반영·실패 등 전달 과정에서 사용자가 알아야 하는 상태와 발신/수신 대상을 조회할 수 있어야 합니다. 메시지 목록의 정확한 화면 구조·상태명·재시도 및 보관 정책은 미확정입니다.
- **`pic` 내부 종료 요청 시** **백그라운드로 유지(최소화/숨김)하거나 실행 중 Agent를 종료할지 사용자에게 선택을 요청**합니다. **백그라운드 유지란 Ghostty 자체를 종료하지 않고 실행 상태로 남겨 Agent와 Split을 유지하는 것**입니다. Ghostty를 완전히 Quit한 뒤에도 Agent만 별도로 계속 실행시키는 것은 현재 선택한 구조의 목표가 아닙니다. Agent 종료 선택 시 실행 중 Agent를 종료하되 **저장된 Pi 대화·Git 파일은 삭제하지 않습니다**. **이 두 선택지는 `pic` 내부 종료 UI에만 적용하며, Ghostty의 `Cmd+Q` 또는 일반 창 닫기 이벤트를 가로채지 않습니다.** Ghostty 자체 종료 동작에 `pic`의 두 선택지가 나타난다고 보장하지 않습니다. (`2026-10-30` 사용자 승인)
- **완전히 종료한 뒤 새로 실행**하는 경우 이전 Main을 자동 선택하지 않고 **사용자가 특정 Main 세션을 선택**합니다. 그 경우 **Main만 재개**하며 이전 Work/Support를 자동 실행하지 않습니다. 작업 중이던 명령을 자동 재실행하지 않습니다. **백그라운드 유지 후 다시 표시하는 경우는 새 실행이 아니라 기존 실행 상태로 복귀**하는 흐름입니다.
- 새로운 Work를 Fork할 때 다른 Work의 **미반영 결정 경고나 자동 동기화는 하지 않습니다.** **현재 Agent 또는 같은 프로덕트에서 `@`로 정확히 선택한 Pi 세션**의 컨텍스트를 Fork합니다.

### Overview의 탐색·배치 정책
- **Agent 생성, 실행 상황 확인, 입력 포커스는 별개의 행동**입니다. 생성한 Work/Support는 Overview의 실제 Ghostty Split에 나타나고 작업을 시작하되, 사용자의 **현재 입력 포커스나 Ghostty Tab을 강제로 전환하지 않습니다**. Main이 별도 Tab에 있어도 현재 Tab을 유지하고 Work는 Overview에 생성합니다.
- 기존 Agent 선택은 **Overview Sidebar가 기본 탐색 수단**입니다. 같은 Overview에서는 Split을 직접 클릭할 수 있습니다. Sidebar는 해당 Agent가 실제로 있는 Tab/Surface에 포커스합니다. 별도 Tab에는 Sidebar를 주입하지 않습니다. 원본 Main 왕복·Agent Switcher 전용 단축키는 기본 필수 기능으로 확정하지 않았습니다.
- Sidebar의 **Main·Work·Support 생성 관계에 따른 중첩 계층과 Agent 위치·순서는 상태에 따라 변하지 않습니다**. 상태별 자동 정렬·완료 시 자동 이동·자동 닫기는 하지 않습니다. 상태 아이콘/텍스트만 갱신하며 상태가 바뀌었다는 이유로 포커스를 가져오지 않습니다.
- 새 Agent는 **생성 순서대로 마지막으로 추가된 Agent 옆에 Split을 추가**합니다. 인위적인 Agent 수 제한이나 임의 자동 정리·접기·Tab 이동을 하지 않습니다. 사용자가 Ghostty의 Resize/Zoom/기본 드래그로 배치를 관리합니다. 공간 부족 시 다른 Agent를 무단으로 닫거나 이동시키지 않고, 실패를 알리고 사용자가 조치하도록 합니다. Ghostty의 실제 한계·Zoom과 Overview 관리 TUI의 관계는 기술 검증 대상입니다.

### Sidebar 상태와 Summary Overlay
- Sidebar는 이름/관계/상태만 간결하게 나타내며 **실행 상태와 새 응답·사용자 개입 표시를 구분**합니다. 실행 중, 입력 대기, 사용자 선택 대기, 응답 종료, 정상 종료, 비정상 종료 및 오류를 실제 근거로 판단합니다. `agent_settled` 등 Pi 이벤트는 **응답이 안정적으로 끝났다는 의미**이지 기능 개발 완료를 뜻하지 않습니다.
- **Agent에 포커스가 있으면 실제 Pi TUI만 표시**합니다. 포커스를 벗어난 지 **30초가 지나면** 진행 Summary Overlay를 표시합니다. 30초 전에 다시 포커스하면 타이머를 취소하고, 다음 포커스 아웃부터 새로 계산합니다. **포커스 없는 Agent의 응답이 종료되면 30초를 기다리지 않고 결과 Summary를 표시**합니다. 포커스 시에는 즉시 Overlay를 해제합니다. 30초는 표시 지연이지 모델 요약 호출 주기가 아닙니다.
- Overlay는 **상태 → 지금 하는 일/결과/필요한 결정(가장 눈에 띄는 문장) → 확인된 주요 근거 1~2개** 순서로 구성합니다. 실행 중이면 지금 진행하는 활동, 응답 종료면 실제 보고한 결과·남은 일·검증 여부, 사용자 판단이 필요하면 결정해야 하는 질문을 우선합니다. Progress %나 단계·성공 여부를 추측해서 만들지 않습니다.
- 최초 지시·Pi 메시지·실제 Tool 실행/결과·확인 가능한 Git 변경을 수집하고, **경량 모델로 근거 기반 의미 요약**을 생성하는 방향을 승인했습니다. Main/Work 모델 대화에 요약을 삽입하지 않으며, 매 Tool 호출이나 30초마다 모델을 호출하지 않습니다. 의미 있는 변화 또는 응답 종료에 갱신하고 변화 없으면 재사용합니다. 정확도·비용·모델/호출 제한은 기술 설계에서 정합니다. Shared Directory에서는 Git 변경 전체를 특정 Agent의 성과로 귀속시키지 않습니다.
- 단순 질문이나 일반적인 '추가 작업할까요?'를 `확인 필요`로 분류하지 않습니다. **사용자 결정 없이는 진행할 수 있다는 명확한 근거**나 명시적인 Pi 선택 UI가 있을 때 표시합니다. `새 응답` 표시는 사용자가 해당 Agent를 확인할 때 해제할 수 있지만, `확인 필요`는 단순 포커스만으로 해제하지 않고 필요한 답변/실제 재개 신호에 따라 갱신합니다. 작업 보고와 실제 구현 완료·테스트 통과는 구분합니다.
- Sidebar 상태는 조용히 갱신하고, 별도 화면 전환·포커스 탈취를 하지 않습니다. 중요한 사용자 개입/실행 실패를 찾기 쉽게 표시합니다. Summary는 Work의 중요한 공유 결정 **후보**도 포함할 수 있으나 Main에 자동 주입하지 않습니다.

### 개별 Agent 중단·종료·재개
- **현재 Pi 응답 중단**은 Pi의 기본 `Esc`를 재사용합니다. Agent 프로세스와 Surface 자체는 유지합니다.
- **Agent 종료**는 Sidebar의 해당 Agent 조작으로 실제 Pi 프로세스/Surface를 종료하는 행동입니다. 응답·명령 실행 중이면 중단 위험을 설명하고 확인하며, 유휴 상태이면 불필요한 확인 없이 종료합니다. 저장된 Pi 대화·현재 Git 파일·Worktree는 삭제하지 않습니다.
- 종료된 Agent는 **Sidebar의 기존 위치와 Main/Work/Support 관계를 유지**하고 `종료됨`을 표시합니다. 사용자가 **종료된 행을 클릭하면 기존 해당 Pi 세션을 곧바로 새 Pi 프로세스/Surface에서 열고** 그 Surface에 포커스합니다. **세션 재개는 이전 대화 복원·입력 대기까지만** 수행합니다. 실제 작업의 지속은 사용자가 `다시 진행해줘` 등 **새 지시를 명시적으로 보낸 뒤** 시작합니다. Work 재개 시 **원본 Pi 세션을 다시 Fork하거나** 이전 지시·실패한 Tool/명령을 자동 재전송·재실행하지 않습니다. 기존 세션/Workspace 부재 시 임의로 새로운 세션을 생성하지 않고 오류를 알립니다.
- 더는 필요하지 않은 **종료된 Agent만 Sidebar에서 제거**할 수 있습니다. 이는 Compose의 관리 목록에서 제외하는 행동이며 Pi 세션 파일·Git 데이터 삭제가 아닙니다. 별도 보관함/보관 해제 기능은 초기 범위에서 제외합니다.
- 사용자가 Pi TUI에서 직접 종료하거나 Ghostty Surface를 닫더라도 **실제 프로세스 상태에 따라 Sidebar를 갱신**합니다. 비정상 종료는 `실행 오류` 등으로 구분하고 응답 완료·개발 완료처럼 표시하지 않습니다. **비정상 종료된 Agent 행을 클릭할 때도 동일하게 기존 Pi 세션만 열고, 중단된 작업은 자동으로 다시 실행하지 않습니다.** 이 종료 감지와 원본 세션 복구, Ghostty 조작의 정확한 연결은 기술 검증 대상입니다.
- **Agent 생성에 실패해도 요청한 Agent의 Sidebar 항목과 생성 요청 Agent·프로덕트 관계를 유지**하고 `시작 실패` 등 실제 근거에 따른 상태를 표시합니다. Pi 세션이 실제로 만들어졌다면 보존하고, 없다면 있다고 가정하지 않습니다. 생성·최초 지시 전송 실패 또는 실행 여부 불명확 상태에서 **자동 재시도·지시 재전송·중복 Agent 생성·임의 Git/세션 정리**를 하지 않습니다. Sidebar에 별도 `다시 시도` 버튼이나 복구 전용 화면을 추가하지 않으며, 확인 가능한 오류 정보를 기존 Overview/터미널 경험에서 제공합니다. 세부 오류 분류·복구 절차는 기술 설계에서 다룹니다.

### 중요 계약 변경의 확인 기준

기존 **도메인·업무 정책, 핵심 사용자 흐름, API/외부 계약, 데이터 의미와 무결성, 보안·권한, 강한 기술 제약, 중요한 기술 선택의 이유**를 변경하거나 훼손할 가능성을 확인합니다.

1. 문장에 적힌 단순 구현 현황과 사용자와 **합의한 계약**을 구분합니다.
2. 새 방법이 기존 선택의 목적을 계속 충족하는지 확인합니다. 기술이 바뀌었다는 이유만으로 반복 승인받지 않습니다.
3. 중요한 기존 목적·제약에 영향을 주고, 사용자가 **그 변경까지 승인했는지 불분명할 때만** 이유와 영향을 설명하고 질문합니다.
4. 명확하게 승인한 계약 변경은 관련 기존 문서에 반영합니다. 이유를 추측하거나 원래 금지 강도를 약화하지 않습니다.

문서화 자체도 유지보수 비용이므로 긴 실행 로그·사소한 리팩터링·모든 대화를 영구 문서로 복제하지 않습니다.

### Work 문서화 범위

Work는 실제 구현에 따라 필요한 설명을 보완할 수 있다는 **후보 방향**이 있습니다. 다만 **어떤 중요 계약을 Work가 자동 수정할 수 있는지, Main과 책임을 어떻게 나눌지는 아직 확정되지 않았습니다.** Main에서 자동 문서화한다는 결정만으로 Work에도 같은 권한이 자동 확장되는 것은 아닙니다.

## 5. 결과·Handoff·Git 통합

- Work의 도구 로그, 추론, 전체 Diff, 테스트 출력, 중요 결정을 **Main 모델 입력에 자동 복사하지 않습니다**.
- **메시지 관리 사이드바**는 사용자가 대상 Agent를 오가며 전달 내역과 상태를 확인하는 별도 진입점입니다. 제품별 보기·Agent별 보기에서 실제 세션의 관계를 탐색하는 것과, 메시지 자체를 관리하는 것은 구분합니다. 사이드바에서 확인한다고 모델이 해당 메시지를 읽은 것으로 간주하지 않습니다.
- Work의 Summary Overlay에는 사용자에게 도움이 될 결과 및 **중요 결정의 공유 후보를 자동 표시**합니다. 이는 후보 안내이며 실제 사용자 승인 여부와 Main 미반영 여부를 근거 없이 확정 표시하지 않습니다.
- **Main으로의 전달:** 사용자가 명시적으로 Main 반영을 요청했을 때만 관련 결정·이유·영향·출처를 전달합니다. 이미 Work에서 사용자가 승인한 결정을 Main에서 무조건 재승인받게 하지 않습니다.
- **Work→Work 전달:** Work A의 Summary Overlay에서 공유 후보를 확인한 **사용자가 수신 Work(예: Work B)와 공유를 명시적으로 선택했을 때만** 전달을 요청합니다. **전달 수단은 `pi-intercom`을 재사용하고, Pi Compose의 작은 Extension이 Summary와 대상 선택·전송 연결을 담당**합니다. 수신 Work B가 Pi 응답을 생성 중이라면 **현재 응답(턴)이 종료된 뒤 모델에 전달**합니다. 진행 중인 턴에 메시지를 끼워 넣어 방향을 바꾸지 않습니다. **Pi 턴 종료와 기능 개발 완료는 다르며**, 기능 개발 완료를 별도로 판단하거나 기다리지는 않습니다. Work A가 대상 Work를 자율 선택하거나 자동 전송하지 않습니다. 실제 턴 종료 감지·지연 전달 구현은 기술 검증 대상입니다.
- 화면에 Summary를 표시하는 것과 Main 모델에 내용을 넣는 것은 별개입니다. Main에서 다음 Work를 Fork하기 전 미전달 결정을 자동 주입하거나 경고하지 않습니다.
- User 요청으로 새 Work에서 문서를 다시 읽을 수 있으나, **다른 Worktree에만 있는 문서 변경이나 Work 대화에서만 정한 사항**은 문서 재조회만으로 자동 공유되지 않습니다.
- 실제 Git 코드·문서 통합/병합 시점은 사용자가 결정합니다. Handoff와 Git 통합은 별개의 동작입니다. Work 응답 종료·테스트 통과를 완료/검증 완료와 혼동하지 않습니다.

## 6. 비목표

## 7. 아직 확정되지 않은 결정

1. **다음 논의:** `pi-intercom` + 작은 Compose Extension에서 **Pi 턴 종료 후 전달**을 어떻게 정확히 구현하고, 수신 메시지의 대기·주입·확인 상태를 어떻게 표현할지. **수신 기준은 현재 Pi 턴 종료로 확정**했으며, 기능 개발 완료를 별도로 판정하지 않습니다. 종료 이벤트·중단/오류 시의 구체적 처리와 성공 확인은 기술 검증/후속 논의 대상입니다.
