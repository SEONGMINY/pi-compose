# PRD — Pi Compose

> **제품 정책의 정본:** 목표 동작의 합의와 코드·실사용 검증은 별개입니다. 현재 실행 가능 여부는 [Usage](USAGE.md)에서 확인합니다.
>
> [비전](VISION.md)과 [사용자 문제](PROBLEM_STATEMENTS.md)는 이 문서의 선행 근거입니다. PRD는 채택한 제품 요구사항만 설명합니다.

## 1. 제품 원칙

- **판단의 맥락:** 확정된 사실·결정 이유·제약과 미결정 사항을 구분해 보존합니다. 일시적인 실행 기록을 Main에 무조건 누적하지 않습니다.
- **위임과 컨텍스트:** 맥락 의존 개발은 실제 Pi Fork, 독립 조사·실행은 별도 Support를 사용합니다. 선택 이유는 [ADR 0001](adr/0001-context-and-delegation.md)에 기록합니다.
- **사용자 통제:** Agent의 보고·검증 주장과 사용자 승인을 혼동하지 않습니다. 사용자 확인 없이 실행·정책 반영·Git 통합을 자동화하지 않습니다.
- **기존 도구 재사용:** Pi·Ghostty·Git의 기능을 우선 이용합니다. 구성 요소의 책임은 [Architecture](ARCHITECTURE.md)에 둡니다.

## 2. Agent와 세션

| 역할 | 주된 일 | 컨텍스트 |
| --- | --- | --- |
| Main | 문제·제품 정책·설계·결정과 이유, 다음 판단 | 원본 Pi 대화 |
| Work | 구현·수정·테스트 코드 작성 등 맥락이 필요한 작업 | 사용자가 선택한 Pi 완료 분기를 실제 Fork |
| Support | 탐색·자료 조사·테스트 실행·독립 검증 | 새 독립 Pi 세션 |

- `pic`은 현재 프로젝트에서 **새 Main**을 직접 엽니다. 별도 Overview를 거치지 않습니다. 기존 저장 세션 복원은 Pi 기본 기능을 사용하며 Work/Support를 임의로 Main으로 바꾸지 않습니다.
- 같은 프로젝트에 여러 Main을 둘 수 있습니다. Fork 원본의 세션·활성 분기, 새 Agent를 요청한 세션, 파일 작업 디렉터리는 각각 구분합니다.
- Main/Work/Support 어느 세션에서도 사용자의 명시적 지시로 Work나 Support를 만들 수 있습니다. Agent 자체의 자율 생성·자동 스케줄링은 현행 범위에 포함하지 않습니다.
- 원본 Pi JSONL은 Fork로 수정하지 않으며, 중단된 도구 호출을 완료 지점으로 잘못 취급하지 않습니다.

## 3. 작업 시작과 Git

- 목표 `pic` 진입은 새 Main 직접 실행이며, 저장된 세션의 복구는 Pi 기본 기능을 사용합니다. 복구한 Work/Support를 Main으로 바꾸지 않습니다.
- `>w 작업`은 현재 Pi 완료 분기의 Work Fork, `>s 작업`은 독립 Support를 뜻합니다. `>>w`·`>>s`는 같은 컨텍스트 계약에 별도의 Git Worktree만 더합니다. `>w @세션 작업`으로 같은 프로젝트의 특정 Fork 원본을 선택할 수 있습니다.
- 새 Agent는 현재 요청한 Pi Terminal을 기준으로 Ghostty Split에서 실행합니다. 기존 Agent의 작업·포커스를 임의 변경하지 않습니다.
- Worktree는 현재 Git HEAD를 기준으로 만들며 미커밋 변경 자동 복사, 브랜치 병합·삭제, 중복 실행·작업 재전송을 추측하여 수행하지 않습니다.

명령어를 실제로 사용할 수 있는 버전과 사용 절차는 [Usage](USAGE.md)를 참고합니다.

## 4. Work → Main Handoff 계약

> **제품 계약:** 아래는 확정된 목표 동작입니다. 미병합 코드·검증 상태는 [Handoff Audit](HANDOFF_IMPLEMENTATION_AUDIT.md)과 해당 PR에서만 확인합니다.

### Work에서 전달

1. Work 입력창에서 `<`를 통해 Main으로의 결과 전달을 시작합니다.
2. 간결한 질문/선택 흐름에서 대상과 **무엇을 보낼지** 확인합니다. 필요한 근거·WHY·조건·범위·검증 상태를 보되 무관한 전체 로그는 전달하지 않습니다.
3. 사용자가 실제 전송을 명시적으로 승인하기 전에는 발송하지 않습니다. 실행 중 Work의 기존 지시나 모델 응답을 Steering·Follow-up으로 바꾸지 않습니다.
4. `< @세션`은 명시적 대상 선택의 후보이며, `<<`에는 별도 의미를 부여하지 않습니다. 세부 UI는 원본 Pi 관례를 먼저 검토합니다.

### Main에서 수신

1. Work에서 발송한 결과가 도착하면 **수신 알림만 표시**합니다. 본문·추가 모델 턴을 Main 컨텍스트에 자동 주입하지 않습니다.
2. 사용자가 수신 내용을 직접 확인한 뒤 필요한 정보만 **명시적으로 컨텍스트에 반영**합니다. 수신·열람·논의·반영·정책 승인을 혼동하지 않습니다.
3. **별도의 Inbox 명령을 필수 UX로 만들지 않습니다.** 기존 PR #25의 영속 로컬 저장은 보존 후보이나, 알림에서 확인/반영하는 정확한 상호작용은 구현 전 검토 대상입니다.
4. Main에 이미 있는 최신 승인 정책과 Work 보고가 충돌할 수 있습니다. Work는 Fork 이후 Main 대화를 몰래 읽지 않으며, Main에서 검토하는 시점의 현재 활성 분기를 기준으로 판단합니다.
5. 정확한 수신 Main과 전달 출처를 확인하지 못하거나 근거가 부족하면 발송/반영을 완료된 것처럼 표시하지 않습니다.

### 구별할 상태

- `Work 보고` ≠ `검증된 사실`; `테스트 코드` ≠ `테스트 통과`
- `전송 요청` ≠ `수신`; `수신 알림` ≠ `Main 모델이 읽음`
- `Main에 참고 정보 반영` ≠ `기존 사용자 정책 변경 승인`
- Handoff와 Git 병합·프로젝트 문서 변경은 독립된 행동

## 5. 프로젝트 문서 관리

- 루트 `AGENTS.md`는 짧은 비전과 주요 코드/문서 위치만 제공합니다. 문서별 정본은 [문서 안내](README.md)에서 관리합니다.
- Main은 사용자의 **명확한 승인**을 확인한 중요한 정책·계약 변경을 해당 정본 문서에 반영합니다. Agent 제안과 미승인 보고는 정책이 아닙니다.
- Work는 실제 개발로 바뀐 구현 설명·기술 사용법을 수정할 수 있지만, **제품 정책·핵심 도메인 계약·중요 기술 결정의 승격/변경을 독자적으로 수행하지 않습니다.** 그런 발견은 Main에 전달해 검토합니다.
- 새 문서 생성은 사용자가 요청하거나 명시적으로 승인한 경우에만 수행합니다. 별도 문서·ADR·DB를 자동으로 늘리거나 같은 계약을 여러 문서에 복제하지 않습니다. 프로젝트 문서 변경과 Pi 대화 롤백은 별개의 작업입니다.

## 6. 비목표

Sidebar·Overview·Summary Overlay, Orca, tmux/workmux, 별도 GUI/상주 서버/메시지 브로커, 자동 멀티 Agent 스케줄링, 자동 정책 승인·Git 병합·세션/Worktree 삭제는 현재 목표가 아닙니다.

## 7. 아직 검증할 조건

- **수신 알림 UX:** Main에서 도착 결과를 어떻게 확인·보류·다시 열고 명시적으로 반영할지. `/compose inbox` 없이 Pi 기본 상호작용을 최대한 재사용하는 방향만 확정됐습니다.
- **검증 경계:** 새 Main·정확한 Fork·Handoff 전달/수신·의미 품질·중단/재개를 각각 확인해야 합니다. 기술적 실패 조건은 [TRD](TRD.md), 남은 실행 순서는 [Implementation Plan](IMPLEMENTATION_PLAN.md)이 정본입니다.
