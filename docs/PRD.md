# PRD — Pi Compose

> 제품 결정 기준: 2026-11-10 · **정책 합의와 코드·실사용 검증은 별개**
>
> [비전](VISION.md)과 [사용자 문제](PROBLEM_STATEMENTS.md)는 이 문서의 선행 근거입니다. PRD는 채택한 제품 요구사항만 설명합니다.

## 1. 제품 원칙

- **Main 컨텍스트 보호:** 사실·선택 이유·강한 제약·미결정을 보존하며 실행 로그와 무관한 결과를 자동으로 쌓지 않습니다.
- **정확한 맥락 상속:** 맥락이 필요한 개발은 실제 Pi 활성 대화의 완료 지점을 별도 Work 세션으로 Fork합니다. Resume이나 모델 요약으로 대체하지 않습니다.
- **독립 작업:** 전체 맥락이 필요 없는 탐색·조사·테스트 실행은 Support에서 처리할 수 있습니다.
- **사람이 결정:** Agent의 제안·보고, 코드 변경, 테스트 실행, 사용자 승인, Main 정책 채택은 서로 다른 사건입니다.
- **기존 도구 우선:** Pi Extension·세션·TUI, Ghostty, Git을 재사용합니다. 자체 Agent 런타임·불필요한 관리 화면을 만들지 않습니다.

## 2. Agent와 세션

| 역할 | 주된 일 | 컨텍스트 |
| --- | --- | --- |
| Main | 문제·제품 정책·설계·결정과 이유, 다음 판단 | 원본 Pi 대화 |
| Work | 구현·수정·테스트 코드 작성 등 맥락이 필요한 작업 | 사용자가 선택한 Pi 완료 분기를 실제 Fork |
| Support | 탐색·자료 조사·테스트 실행·독립 검증 | 새 독립 Pi 세션 |

- `pic`은 현재 프로젝트에서 **새 Main**을 직접 엽니다. 별도 Overview를 거치지 않습니다. 기존 저장 세션 복원은 Pi 기본 기능을 사용하며 Work/Support를 임의로 Main으로 바꾸지 않습니다.
- 같은 프로젝트에 여러 Main을 둘 수 있습니다. Fork 원본의 세션·활성 분기, 새 Agent를 요청한 세션, 파일 작업 디렉터리는 각각 구분합니다.
- Main/Work/Support 어느 세션에서도 사용자의 명시적 지시로 Work나 Support를 만들 수 있습니다. Agent 자체의 자율 생성·자동 스케줄링은 현행 범위에 포함하지 않습니다.
- 원본 Pi JSONL은 Fork로 수정하지 않으며, 중단된 도구 호출을 완료 지점으로 잘못 취급하지 않습니다.

## 3. 작업 시작과 Git

| 입력 | 컨텍스트 | 파일 공간 |
| --- | --- | --- |
| `>w 작업` | 현재 Pi 완료 분기 Fork | 입력 Agent의 현재 디렉터리 공유 |
| `>w @세션 작업` | 같은 프로젝트에서 명시적으로 선택한 Pi 세션 Fork | 입력 Agent 디렉터리 공유 |
| `>>w 작업` | 현재 완료 분기 Fork | 입력 Agent의 Git HEAD 기반 새 Worktree |
| `>>w @세션 작업` | 선택한 세션 Fork | 입력 Agent의 Git HEAD 기반 새 Worktree |
| `>s 작업` | 독립 Support | 입력 Agent 디렉터리 공유 |
| `>>s 작업` | 독립 Support | 입력 Agent의 Git HEAD 기반 새 Worktree |

- 직접 위임은 Pi 입력 첫머리에서만 해석합니다. `>`는 디렉터리 공유, `>>`는 새로운 Worktree를 뜻합니다. 작업 지시가 없으면 Agent를 실행하지 않습니다.
- 새 Agent는 현재 Pi가 실행 중인 Ghostty Terminal을 기준으로 별도 Native Split에 엽니다. 기존 Agent의 프로세스·Pi 세션·포커스를 임의로 교체하지 않습니다.
- 미커밋 변경은 Worktree에 자동 복사하지 않습니다. Git 병합·Worktree 삭제·세션 삭제를 자동으로 실행하지 않습니다.
- 실패·취소·재개 과정에서 중복 실행 또는 최초 지시 자동 재전송을 추측해서는 안 됩니다.

## 4. Handoff — 확정된 신뢰 경계와 한 번 승인

> **2026-11-11 원칙 확정:** Work는 원본 출처·필수 WHY/제약·검증 상태를 갖춘 보고를 준비하고, 사용자는 **전달할 범위와 정확한 본문을 Work에서 한 번 승인**합니다. Main은 수신된 Work를 다시 작성하거나 구현/테스트를 반복 심사하지 않습니다. 원본 수신과 **활성 Main 모델 컨텍스트 반영**은 별개이며, 반영 전에는 현재 Main의 최신 결정과 정합성을 확인합니다. 이 원칙은 설계 계약이고 PR #25의 현재 실행 성공을 뜻하지 않습니다.

### Work — 준비 및 발신 책임

1. Work에서 `<`로 Handoff를 시작합니다. Work는 **Fork 당시의 Main 컨텍스트와 자신의 작업 기록**으로 작업 결과, 근거 원문, 필수 WHY/조건/부정문, 검증·미검증 상태를 연결합니다. 빠진 근거를 추측해 채우거나 미실행 테스트를 성공으로 표현하지 않습니다.
2. 사용자는 **Main에 전달할 결과가 무엇인지** 먼저 이해하고 포함할 항목을 조정합니다. 세부 Entry ID/긴 인용문은 필요할 때 열고, 최종 승인 전 **실제 Main에 추가될 본문**을 검토합니다. 필수 제약은 결과와 함께 보존합니다.
3. 사용자가 정확한 Handoff 본문 전송을 한 번 승인하기 전에는 발송하지 않습니다. 이 승인은 **전달 범위의 승인**이지 모든 주장에 대한 독립 검증이나 새로운 Main 정책 승인이 아닙니다.
4. `< @세션`의 명시적 대상 선택은 별도 UX 검토 대상으로 두며 `<<`에는 임의 의미를 부여하지 않습니다.

### Main — 원본 수신과 컨텍스트 반영은 별개

1. 승인된 원본 Handoff 패키지는 출처·대상·해시·Fork 계보를 확인해 **Main 모델 컨텍스트 바깥의 영속 저장소에 수신**합니다. 수신 자체에는 두 번째 사용자 승인, Main 모델 턴, 코드/정책 수정이 필요하지 않습니다.
2. **활성 Main 분기에 참고 보고로 넣기 전** Fork 이후 Main에서 확정되거나 변경된 관련 결정과의 정합성 및 중복 여부를 확인합니다. Work가 Fork 이후 Main의 새 결정을 알고 있었다고 추측하지 않습니다. Main은 Work 파일 생성·테스트 실행을 Main 대화만 근거로 재판정하지 않습니다.
3. 정합성이 확인된 신규 결과는 Work에서 승인한 **동일한 본문을 출처 표시된 참고 보고**로 기록합니다. 모델 턴이나 정책 승인을 자동으로 시작하지 않고, Pi 기록 receipt를 확인한 후에만 반영 완료로 표시합니다.
4. **정책 충돌·최신 결정의 검증 불가**가 있다면 원본은 외부 보관 상태로 유지하고 기존 Main 정책을 보존합니다. *확인된 충돌*과 *정보 부족*을 같은 사용자 결정 문제로 취급하지 않습니다. 모델/파싱/전달 오류는 기술적 실패로 분리해 재시도·상태 안내하고, 사용자가 실제 결정을 내려야 할 때만 예외 검토를 요청합니다.
5. Main이 꺼져 있으면 원본을 보관하고 해당 Main 재개 시 처리합니다. 이미 반영된 내용은 다른 활성 분기에 임의 재주입하지 않으며 중복 보고와 반영 receipt를 구별합니다.

### 구분해야 할 신뢰 수준

- **전달 무결성:** 출처·원문·승인 본문/해시·분기 계보를 확인했다는 의미. 진술한 작업 결과의 사실성까지 증명하지 않음.
- **작업 검증 상태:** Work의 보고·실제 검증 증거·미실행 항목을 구분. 사용자 전송 승인만으로 테스트 성공이 되지 않음.
- **Main 정합성:** Fork 이후 현재 Main의 확정 결정과 정합성 확인. 원본 수신은 정책 채택이 아니며 참고 보고 반영도 기존 정책 변경 승인이 아님.
- Handoff 수신/활성 컨텍스트 반영, Git 병합, 파일 수정, 정본 문서 갱신은 각각 별개의 행동.

**구현 경계:** 기존 PR #25는 Main에서 Work 결과 전체를 `new/duplicate/conflict/insufficient`로 의미 비교하고 `insufficient`도 일괄 보류할 수 있습니다. 이는 이번에 확정한 **Work 결과 재심사 금지** 및 **기술적 검증 실패와 정책 충돌의 분리**와 아직 일치하지 않습니다. 코드와 UX를 이 원칙에 맞춰 변경하고 별도로 검증해야 합니다.

## 5. 프로젝트 문서 관리

- 루트 `AGENTS.md`는 짧은 비전과 주요 코드/문서 위치만 제공합니다. 문서별 정본은 [문서 안내](README.md)에서 관리합니다.
- Main은 사용자의 **명확한 승인**을 확인한 중요한 정책·계약 변경을 해당 정본 문서에 반영합니다. Agent 제안과 미승인 보고는 정책이 아닙니다.
- Work는 실제 개발로 바뀐 구현 설명·기술 사용법을 수정할 수 있지만, **제품 정책·핵심 도메인 계약·중요 기술 결정의 승격/변경을 독자적으로 수행하지 않습니다.** 그런 발견은 Main에 전달해 검토합니다.
- 새 문서 생성은 사용자가 요청하거나 명시적으로 승인한 경우에만 수행합니다. 별도 문서·ADR·DB를 자동으로 늘리거나 같은 계약을 여러 문서에 복제하지 않습니다. 프로젝트 문서 변경과 Pi 대화 롤백은 별개의 작업입니다.

## 6. 비목표

Sidebar·Overview·Summary Overlay, Orca, tmux/workmux, 별도 GUI/상주 서버/메시지 브로커, 자동 멀티 Agent 스케줄링, 자동 정책 승인·Git 병합·세션/Worktree 삭제는 현재 목표가 아닙니다.

## 7. 미결정과 완료 기준

- **예외 수신 UX (설계 논의 중):** Main `<`는 사용자 판단이 실제 필요한 정책 충돌 등을 위한 경로로 한정합니다. 단순 비교 모델 오류, 실행 증거 부족, 전달 오류를 사용자 정책 결정과 혼동하지 않도록 상태·UI를 분리해야 합니다.
- **후보 준비:** 새 기본 경로에서는 Work `<` 요청 시 후보·필수 맥락을 준비합니다. 과거 자동 완료 후보 및 질문 코드는 역사적 구현이지만 최신 기본 경로에서 등록하지 않습니다. 자동 Main 전송은 허용하지 않습니다.
- **모델의 불완전한 근거:** 불완전한 분석을 안전·정합성 확인 완료로 간주하지 않습니다. 모델 실패의 자동 복구 방식, 보고를 컨텍스트 외부에 보류할 조건과 실제 사용자 판단을 요구할 조건은 TRD/계획에서 구체화합니다.
- **실제 검증:** 새 Main/정확한 Fork/Native Split/Work `<`/Main 알림·반영/원문·의미·정책 보호/종료·재개의 macOS 실사용 확인이 필요합니다.
- 코드 존재, 타입·단위 테스트 통과, 실제 실행 성공, Handoff 의미 품질은 각각 별도로 입증합니다.
