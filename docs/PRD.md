# PRD — Pi Compose

- 최신 제품 결정: **2026-11-09 — Sidebar 제거, Main 직접 실행, Work 완료 시 공유 후보 자동 준비(A안), 검토·전송은 사용자 통제**
- 상태: **제품 정책 확정 / 새로운 직접 실행·대기형 Handoff 코드는 작업 브랜치에 반영, 실사용 검증 전**
- 제품: Pi 기반의 조합 가능한 Coding Agent Harness

## 1. 해결하려는 문제

Main에서는 서비스 개발에 필요한 **고품질 맥락**을 쌓습니다. 문제와 목적, 도메인 스토리텔링과 사용자 흐름, 요구사항과 완료 조건, API·데이터 계약, 아키텍처, 제약, 고려한 대안, 결정의 결과 **및 이유**, 아직 결정되지 않은 사항 등이 포함됩니다.

여기서 고품질은 정보가 많다는 뜻이 아니라 **다음 판단을 올바르게 할 수 있도록 사실·결정·제안·불확실성이 정확히 구분되고 중요한 이유가 보존된 상태**를 뜻합니다. 잘못된 답변이 들어간 경우 사용자는 Pi 대화 트리의 이전 지점으로 돌아가 올바른 분기에서 논의를 계속할 수 있습니다.

긴 개발·탐색·오류·테스트·Diff 기록을 Main에 쌓으면 컨텍스트를 소모합니다. 반대로 새로운 Agent에게 짧은 요약만 주면 '왜 금지했는가', '절대 금지'의 강도, 거절한 대안이 사라질 수 있습니다.

**목표:** Main의 맥락을 지키면서 실제 구현과 독립 실행을 분리하고, 다중 작업의 상태·결과는 쉽게 파악하되 불필요한 정보를 Main 모델에 자동 전달하지 않습니다.

## 2. Agent 역할과 컨텍스트

| 구분 | 책임 | 컨텍스트 |
| --- | --- | --- |
| **Main** | 기획·요구사항·도메인·설계·중요 결정·다음 판단 | 실제 원본 Pi 대화. 여러 Main 가능 |
| **Work** | 맥락을 알아야 하는 개발·테스트 코드 작성·반복 수정 | **현재 Agent 또는 같은 프로덕트에서 명시적으로 선택한 Pi 세션**의 활성 분기 마지막 완료 지점을 실제 별도 Pi 세션으로 Fork |
| **Support** | 코드 탐색, 웹 조사, 테스트 **실행**, 독립 검증 | Main/Work 전체 대화를 상속하지 않는 독립 Pi 세션 |

- Fork는 **짧은 요약 전달이나 Resume로 대체하지 않습니다**. **선택한 모든 Pi 원본 세션의 JSONL을 변경하지 않으며**, 실제 Fork 시점과 출처를 검증합니다.
- **Main·Work·Support 어느 Pi 입력창에서든** 사용자가 명시적으로 요청하면 새 Work/Support를 실행할 수 있습니다. Agent 역할에 따른 생성·중첩 제한이나 임의의 깊이 제한을 두지 않습니다. **사용자 직접 위임**과 **Agent가 스스로 다른 Agent를 생성하는 자율 위임**은 별개이며, 자율 위임 권한은 후속 정책 결정 대상입니다. 임의의 자동 작업 스케줄링은 도입하지 않습니다.
- **Fork 원본 Pi 컨텍스트, 새 Agent를 요청한 세션, 실제 파일 작업 디렉터리**는 서로 다른 개념입니다. Fork/Independent 선택과 Shared Directory/Git Worktree 선택을 분리하고, 누가 누구를 생성했는지와 어떤 세션을 Fork했는지 별도로 보존합니다. 순차/병렬 여부는 작업에 따라 결정하며 Pi Extension의 사용 자유도를 유지합니다.
- 예: 기능 의도를 알아야 하는 테스트 **작성**은 Work에 맡기고, 테스트 **실행**은 Support에서 처리할 수 있습니다. 오류 로그를 받은 후 원래 맥락을 가진 Work에서 수정합니다.

### 프로덕트와 Main 관계

- 프로덕트는 **현재 작업 디렉터리로 식별되는 프로젝트**입니다. 하나의 프로젝트에 여러 Main을 둘 수 있으며, bare `pic`은 매번 새 Main을 만듭니다.
- 기존 세션 조회·복구는 Pi의 `--resume`/`-r`, `--continue`/`-c`, `--session`, `/resume` 기능을 재사용합니다. `-c`는 Main 우선 복구가 아니라 Pi의 최근 세션 복구입니다.
- 저장된 Work/Support는 기존 역할·출처를 유지하고 Main으로 자동 전환되지 않습니다. Overview, 전체 Agent 목록 Sidebar, 제품 탐색 UI는 더 이상 목표가 아닙니다.

### 위임 입력의 제품 정책 (2026-10-31 확정)
- 기본 Pi 입력창에서 **단축어 + 자연어**와 **일반 자연어로 Agent에게 위임 요청**하는 두 경로를 제공합니다. 명시적 위임은 **Main·Work·Support 어느 입력창에서도 가능**하며, 단축어는 입력 **첫머리**에서만 해석합니다. 일반 문장에 있는 `>`나 기존 Pi 문법은 침범하지 않습니다. **Compose 전용 키보드 단축키를 추가하거나 Pi/Ghostty 키 바인딩을 변경하지 않습니다.**
- **명령어와 기본 Workspace는 다음과 같이 고정**하며, 이전 선택을 기억하지 않고 Workspace 선택창도 추가하지 않습니다.

  | 직접 위임 | Agent의 컨텍스트 | 파일 작업 공간 |
  | --- | --- | --- |
  | `>w 작업 지시` | 현재 Pi 세션의 완료 지점 Fork | **명령어를 입력한 Agent의 현재 디렉터리 공유** |
  | `>w @세션 작업 지시` | 선택한 같은 프로덕트 세션 Fork | 명령어를 입력한 Agent의 현재 디렉터리 공유 |
  | `>>w 작업 지시` | 현재 Pi 세션의 완료 지점 Fork | **새 Git Worktree** |
  | `>>w @세션 작업 지시` | 선택한 같은 프로덕트 세션 Fork | **새 Git Worktree** |
  | `>s 작업 지시` | **독립 Pi 세션**, Fork 없음 | 명령어를 입력한 Agent의 현재 디렉터리 공유 |
  | `>>s 작업 지시` | **독립 Pi 세션**, Fork 없음 | **새 Git Worktree** |

- `>w`/`>>w`에서 원본을 지정하지 않으면 **명령을 입력한 현재 Agent**를 Fork합니다. 현재 세션이 Support라도 명시적으로 요청한 Work의 Fork 원본이 될 수 있습니다. `>s`/`>>s`는 독립 Support이므로 Fork 원본 선택 `@세션`을 사용하지 않습니다. **다른 프로덕트의 세션은 Fork 검색·선택 대상에서 제외**합니다.
- 네 가지 직접 위임 명령은 **입력한 Agent의 모델을 호출하거나 그 대화에 요청을 남기지 않고** 처리합니다. **단축어와 선택용 `@세션` 토큰을 제외한 사용자의 작업 지시 원문**을 새 Agent의 최초 지시로 전송하고 생성과 함께 실행을 시작합니다. Work의 컨텍스트는 **선택한 원본 Pi 세션을 실제 Fork**하며 모델이 재작성한 요약으로 대체하지 않습니다.
- 일반 자연어 위임은 **입력한 Agent의 모델**이 읽고 판단하므로 그 위임 요청이 해당 Agent 대화에 남는 것을 허용합니다. 명시적 실행 의도·Fork 원본·Workspace 등 필수 정보가 분명하면 반복 확인 없이 실행하고, 모호한 요청을 임의로 자동 실행하지 않습니다. **모델의 자율적 다단계 재위임 허용 범위는 별도 결정 전까지 확정하지 않습니다.**
- `>w`/`>s`/`>>w`/`>>s` 뒤에 작업 지시가 없으면 즉시 Agent를 실행하지 않습니다. 입력 중인 텍스트는 취소·실패 시 가능한 한 보존합니다. 지시 없이 Agent를 생성하는 Overview UI는 제공하지 않습니다.
- **`>w @` / `>>w @` 세션 자동완성**은 **현재 프로덕트**의 Main·Work·Support 중 **실행 중이거나 종료되어 기록이 남은 Pi 세션**을 검색합니다. 세션 **이름 + 최근 실제 작업을 설명하는 한 줄 + 작업 디렉터리/Worktree 정보**를 표시하고, 이름·최근 작업 내용으로 검색합니다. 실제 선택값은 표시 이름이 아닌 **고유 Pi 세션 ID**로 식별합니다. 작업 설명은 기존 Summary 등 근거 있는 정보를 재사용하며 입력마다 LLM을 호출하지 않습니다. 의미 있는 Summary가 없다면 확인 가능한 최근 작업 지시를 표시합니다. 일반 `@` 파일 검색은 그대로 유지합니다.
- **`>`는 현재 디렉터리 공유**, **`>>`는 새 Git Worktree 생성**을 의미합니다. `@세션`으로 **Fork 대화**를 바꾸어도 **파일 작업 공간은 명령을 입력한 현재 Agent 기준**으로 결정합니다. 새 Worktree는 **명령 입력 Agent의 현재 브랜치 HEAD**를 시작점으로 별도 브랜치/체크아웃을 만들고, 원본 브랜치·디렉터리는 변경하지 않습니다. 미커밋 변경은 복사하지 않으며, 변경 사항이 있다면 그 사실을 알리되 매번 확인·커밋을 강제하지 않습니다. Git Merge·Worktree 자동 삭제도 하지 않습니다.

## 3. 실행 환경·세션·화면

- **Pi + Ghostty Native Split**만 사용합니다. Orca, tmux/workmux, Herdr App/core, 별도 GUI·서버·멀티플렉서는 도입하지 않습니다.
- `pic`은 현재 터미널에서 **새 Main을 직접 실행**합니다. 자동 복구, 기존 Main 선택 UI, Sidebar/Overview는 없습니다. Main에는 자동 업무 지시를 보내지 않습니다.
- 사용자는 필요할 때 `>w`, `>s`, `>>w`, `>>s`로 Work/Support를 생성합니다. 새로운 Agent는 **입력을 받은 Pi의 현재 Ghostty Surface**를 기준으로 Split합니다. 사용자의 입력 포커스를 강제로 이동시키지 않고, 정확한 Pi Fork/독립 Support·Git Worktree 의미를 지킵니다.
- 기존 Agent는 Ghostty Split과 Pi 세션을 유지합니다. 사용자는 Ghostty의 기본 기능으로 화면 크기·Tab 배치를 관리하며, Compose는 임의로 다른 Agent의 작업을 중단하거나 Surface를 닫지 않습니다.
- 세션 복구는 사용자의 명시적 Pi 명령으로 합니다. 이전 명령·도구 실행·Agent 생성은 자동 재실행하지 않으며, 저장된 Git·대화 기록을 임의로 삭제하지 않습니다.
- Pi 기본 Esc 등 중단 기능과 Pi 기본 세션 선택기를 재사용합니다. Compose 전용 Sidebar 종료 선택·프로세스 관리 UX는 범위에서 제외합니다.

### Work 실행 중 Handoff 요청

- Work가 모델 응답·도구 실행 중일 때도 사용자는 `<` 또는 `< @세션`으로 Handoff를 **요청**할 수 있습니다.
- 요청은 모델 Steering·Follow-up 메시지가 아닙니다. Work 작업을 중단하거나 기존 결과·제약을 변경하지 않습니다.
- **A안:** `<` 요청이 없어도 Work가 작업을 완료했다고 명시적으로 보고한 경우, 실행 종료 뒤 별도 모델 호출로 중요한 결과·제약·미결정 사항의 공유 후보와 원문 근거를 준비하고 **Work 세션에 보관**합니다. 단, `agent_settled`만으로 실제 기능 완료·검증 완료를 추정하지 않습니다.
- 후보 생성·저장은 **사용자가 답할 때까지 기다리지 않으며**, 다른 Agent의 포커스를 가져오지 않습니다. 후보가 있으면 원본 `ask_user`가 설치·활성화된 경우 Work에서 다중 선택·자유 입력·추가 의견을 받는 검토 턴을 엽니다.
- 사용자는 나중에 Work에 돌아와 후보를 선택하거나 수정 방향을 제시합니다. 필요한 경우 `/compose review`로 저장된 후보를 다시 열 수 있습니다. 선택한 내용으로 Work 모델이 초안을 작성하면 **본문 편집·별도 전송 승인 단계까지 자동으로 이어집니다.** `<` 재입력은 필요하지 않습니다. 후보 선택 자체는 전송 승인이 아닙니다.
- `<`는 독립적인 수동 Handoff 진입으로 유지하며, 저장된 후보·사용자 의견이 있다면 그 결과를 우선 사용합니다. 최종 본문은 Pi 에디터에서 수정하고 별도 전송 확인을 받습니다.
- 중복 요청·세션/분기 전환·중단·오류의 경우 오래된 작업을 완료 결과로 오인하지 않습니다. 대기 요청은 프로세스 메모리 수준의 임시 상태이며 재시작 후 보존을 보장하지 않습니다.
- `<<`는 미지원입니다.

### 전달 상태와 Main 안전선

- Handoff 발송 요청, intercom 전달 확인, 수신 Main 모델의 처리·채택은 **서로 다른 증거**입니다.
- Handoff를 수신했다는 이유로 Main의 기존 정책을 변경하거나 새 작업을 자동 시작하지 않습니다.
- Work의 추론·도구 로그·전체 Diff는 Main에 자동 복사하지 않습니다. 필요한 사실·제약과 원문 출처만 선택적으로 전달합니다.

## 4. 문서로 맥락 보존

| 영역 | 확정 정책 |
| --- | --- |
| 원본 | Main의 실제 Pi 대화 + 프로젝트의 **기존 원본 `docs/*` 문서** |
| 문서 진입점 | 짧은 `AGENTS.md`가 각 문서가 무엇을 다루는지 안내 |
| 자동 갱신 대상 | **사용자가 명확히 승인한 중요한 결정**. 검토 중 의견·Agent 혼자 낸 제안은 제외 |
| 실행 시점 | 승인 **직후** 관련 기존 문서를 갱신 |
| 새 문서 | 생성 전 사용자 확인 필요; 같은 계약을 여러 문서에 중복 기록하지 않음 |
| 수동 조작 | 사용자는 언제든 문서화를 요청할 수 있음 |
| 대화 롤백 | 프로젝트 문서·Git은 자동으로 되돌리지 않음. 사용자가 Git 또는 명시적 Agent 요청으로 되돌림 |
| 초기 구현 | **작은 프로젝트 지침 + Pi 기본 파일 도구**. 실제 누락이 발생하기 전 자동 감시 Extension/DB를 만들지 않음 |
| 맥락 불러오기 | 설계 정보가 부족한 세션은 **사용자가 요청할 때만** 관련 문서를 선택적으로 읽음. Skill은 후보 |

### 중요 계약 변경의 확인 기준

기존 **도메인·업무 정책, 핵심 사용자 흐름, API/외부 계약, 데이터 의미와 무결성, 보안·권한, 강한 기술 제약, 중요한 기술 선택의 이유**를 변경하거나 훼손할 가능성을 확인합니다.

1. 문장에 적힌 단순 구현 현황과 사용자와 **합의한 계약**을 구분합니다.
2. 새 방법이 기존 선택의 목적을 계속 충족하는지 확인합니다. 기술이 바뀌었다는 이유만으로 반복 승인받지 않습니다.
3. 중요한 기존 목적·제약에 영향을 주고, 사용자가 **그 변경까지 승인했는지 불분명할 때만** 이유와 영향을 설명하고 질문합니다.
4. 명확하게 승인한 계약 변경은 관련 기존 문서에 반영합니다. 이유를 추측하거나 원래 금지 강도를 약화하지 않습니다.

문서화 자체도 유지보수 비용이므로 긴 실행 로그·사소한 리팩터링·모든 대화를 영구 문서로 복제하지 않습니다.

### Work 문서화 범위

Work는 실제 구현에 따라 필요한 설명을 보완할 수 있다는 **후보 방향**이 있습니다. 다만 **어떤 중요 계약을 Work가 자동 수정할 수 있는지, Main과 책임을 어떻게 나눌지는 아직 확정되지 않았습니다.** Main에서 자동 문서화한다는 결정만으로 Work에도 같은 권한이 자동 확장되는 것은 아닙니다.

## 5. 결과·Handoff·Git 통합

- Handoff는 **사용자가 명시적으로 지정한 수신자와 전송 대상**에게만 전달합니다. 연결된 정확한 Pi Session ID와 intercom 주소가 확인되지 않으면 이름·cwd로 추측해 전송하지 않습니다.
- Handoff 초안은 최근 완료 Work 보고, 원 사용자 지시 및 도구 출력에서 관련 원문을 선택하고 Pi Entry ID와 대조합니다. 원문 문자열이 일치한다는 사실만으로 의미 정확성을 보장하지 않으므로 부정, 승인 주체, 검증 상태를 보수적으로 유지합니다.
- `/compose handoff`는 기존 수동 경로, `/compose messages`는 근거가 확인된 기록 조회 경로로 유지합니다.
- 사용자가 확인하지 않은 Work의 발견·제안·결정은 Main에 전송하지 않습니다. Work가 이미 사용자로부터 명시적인 승인을 받은 사실을 임의로 재승인받게 하지도 않습니다.
- Work→Work 전달도 사용자가 대상과 내용을 명시적으로 선택합니다. 현재 받는 Pi 응답에 메시지를 끼워넣지 않는 pi-intercom의 human-first 전달 계약은 유지합니다.
- Handoff는 Git 브랜치 병합, 문서 수정, Main 기록 동기화와 독립된 행동입니다. `>>`의 Git Worktree를 자동 Merge/삭제하지 않습니다.
- **대화형 수정:** `pi-ask-user`의 원본 `ask_user`가 후보 선택·자유 입력·추가 의견을 받고, Work 모델이 이를 반영해 검토용 초안을 작성합니다. `ask_user`는 모델 전용이므로 Compose 자체 모델 생성 호출과 별도로 Work의 도구 호출 턴을 사용합니다. **코드 작성 단계이며 실제 통합 검증 전**입니다.

## 6. 비목표와 현재 구현 상태

자체 Pi 런타임, 재작성된 Compaction·Fork 엔진, 자체 Agent 메시지 브로커, 자동 Git 병합·삭제, DB, 자동 Agent 생성·스케줄링, Sidebar·Overview·Summary Overlay·별도 GUI는 비목표입니다.

`main`에는 이전 Overview 기반 코드가 남아 있습니다. `feat/pic-direct-main-handoff-20261109` 작업 브랜치에서는 직접 Main 실행, 현재 터미널 기준 Ghostty Split, 실행 중 Handoff 요청 보관·응답 종료 후 사용자 검토 경로를 구현하고 있습니다. **코드 작성과 타입/실행/macOS 실사용 검증은 구분**합니다.

## 7. 기술 검증 및 후속 결정

1. Pi 1.4.0/Ghostty macOS에서 Main 직접 실행·세션 ID 기록·Ghostty 현재 Surface Split, Pi 세션 Resume의 실제 동작 검증.
2. Work 응답 중 `<`가 일반 모델 입력이 아닌 독립 요청으로 처리되는지, `agent_settled`와 취소/중단/분기 변경에 대해 안전하게 작동하는지 검증.
3. `pi-intercom@0.18.1`의 `/handover` 로딩/취소/편집과 `pi-ask-user` 질문 흐름을 재사용할 수 있는지 버전별 원본 코드와 실제 실행을 대조. `ask_user`는 모델 전용 도구이므로 설치만으로 Compose 초안 생성에 연결되지 않음.
4. 기존 Handoff 실험의 제약 누락·부정문·승인 오인·테스트 미실행/미확인 사례를 회귀 검증. 장문 무차별 요약이 우월하다고 가정하지 않음.
5. 위 검증에서 원본 기능으로 해결할 수 없는 실제 공백이 드러난 경우에만 새 UX·API를 사용자와 논의합니다.

> **우선순위:** 최신 사용자 결정(2026-11-09) → 이 PRD → Architecture/TRD/Plan → 현재 코드 → 과거 ADR/PR. 과거 Overview·Sidebar·Summary Overlay 구현 기록은 현재 제품 정책의 근거가 아닙니다. 문서·코드 변경만으로 실사용 검증을 완료했다고 표현하지 않습니다.


## Handoff P1–P5 · 2026-11-10 제품 계약 (기존 계약의 후속 변경)

- **Work 생성/완료/ask_user** 기존 성공 경로를 유지하며, 선택한 제목이 아닌 고정 후보 ID를 공유 범위의 근거로 사용합니다.
- **B안**: 선택된 후보와 그것을 오해 없이 이해하는 데 필요한 출처·조건·WHY·범위·검증 상태만 포함합니다. 선택하지 않은 무관한 후보는 금지합니다.
- **A안(Work 경계)**: Work는 Fork 당시의 원문과 이후 자신의 활성 분기만 읽으며, Fork 이후 Main의 대화를 참고하지 않습니다. Work가 본 사용자 지시는 Fork 시점의 과거 기록일 수 있습니다.
- **A안(Main 시점)**: Main에 Handoff가 도착하면 모델 실행 및 대화 주입 없이 보관합니다. 사용자 `/compose inbox` 항목 선택 시에만 그 순간의 활성 Pi 분기와 비교합니다.
- **검토**: Pi의 Compaction·ContextEdit 반영된 최신 컨텍스트에서 확인된 신규 가능성/중복/충돌/판단 불가를 구분합니다. ID 존재 또는 문자 일치만으로 인과·의미·결정 권위가 증명되지 않습니다.
- **전달 승인**: Work가 선택 범위와 출처를 근거로 구성한 정확한 본문을 사용자가 미리보고 승인합니다. 승인 이후 본문 재생성·변경을 금지합니다. 보완 요청 시 다시 근거 검색 및 검증합니다.
- **Main 선택**: `D`는 대화에서 논의, `I`는 비교상 신규 가능성이 있는 Work 보고만 기록하는 별도 명시적 행동입니다. I도 외부 보고를 승인 정책으로 승격하지 않습니다. 기존 사용자 결정과 관련 계약 변경은 별도 사용자 승인 없이는 실행하지 않습니다.
- **보호**: Main 수신은 local durable inbox에 기록하고 pi-intercom Extension Channel은 비컨텍스트 알림으로만 사용합니다. 일반 intercom Outbox가 보호형 Work→Main 경로를 우회하지 않습니다.
- **검증**: 기존 실험에서 관측된 부정문 반전, 사용자 승인 귀속 오류, 미확인/미실행/통과 혼동, WHY 누락, Fork 이후 최신 결정 충돌을 회귀 검증합니다. 연구의 결과를 곧바로 새로운 구현의 성공률로 주장하지 않습니다.
- **범위**: 우선 동일 macOS 사용자 계정의 로컬 Pi 세션, 하나의 정확한 대상 Main ID. 원격/다중기기 자동 동기화와 Handoff 수신에 따른 자동 구현·Git 병합은 포함되지 않습니다.
