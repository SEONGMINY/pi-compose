# PRD — Pi Compose

- 상태: **핵심 제품 요구사항 합의됨** / 세부 구현 및 기술 호환성 검증 전
- 작성일: 2026-10-25
- 제품 설명: **A composable coding agent harness built on Pi.**
- 배경: [AS-IS와 문제](domain-stories/01-as-is-and-pain-points.md) · [TO-BE 시나리오](domain-stories/02-to-be-and-scenarios.md)
- 관련 기술: [TRD](TRD.md) · [Architecture](ARCHITECTURE.md)

## 1. 목표와 비목표

### 목표

1. 사용자가 Pi 기반 코딩 에이전트를 **작업의 성격에 따라 조합**하고, 준비·인계·검증의 반복 조작을 줄인다.
2. Main Agent에 축적된 **결정의 원인·강한 금지사항·거절한 대안·사용자 의도**를 가능한 온전하게 유지한다.
3. 독립적인 탐색·조사·테스트·Diff 검증을 Main의 활성 컨텍스트 바깥에서 처리한다.
4. 개발자는 실행할 작업과 방법, 주요 계약 결정, Git 통합 시점을 직접 통제한다.
5. 특정 프로젝트·프레임워크·Git 작업 공간 방식에 종속되지 않는 개인용 범용 Harness를 제공한다.
6. 기본 Launch를 유지하되 View와 부가 Extension은 사용자가 선택할 수 있게 한다.

### 비목표 / 명시적 제외

- 자체 LLM Runtime, Pi 세션 저장 엔진, 자체 Compaction 엔진 또는 View/Plugin Registry 개발.
- 자동 개발 에이전트 스케줄러, 사용자 승인 없이 순차 개발을 자동 위임하는 오케스트레이터.
- 모든 작업에 Worktree·병렬 처리·독립 Agent를 강제.
- 프로젝트 계약을 새 DB·DSL·자동 생성 문서로 복제·대체.
- 모든 변경을 에이전트 전체에 방송하거나 Main을 통신 중계자로 사용.
- 모든 작업에 필수 AI 리뷰·다단계 사람 승인 Gate 추가.
- 전용 Git 병합 엔진, 사용자 데이터 강제 삭제·자동 병합.
- 모든 프로젝트에 특정 보안·계약·정적 분석 도구 일괄 설치.
- 테스트 통과나 리뷰 결과를 곧바로 사용자 의도 준수의 증거로 간주.

## 2. 대상 사용자와 개념

**주 사용자:** 여러 코드베이스에서 Pi 기반 코딩 에이전트를 사용하는 개발자.

| 용어 | 뜻 |
| --- | --- |
| Main Agent | 장기간 요구사항·설계·의사결정 맥락을 축적한 중심 대화 |
| Fork | 지정된 Pi 원본 세션의 컨텍스트를 새 세션에 이어받음. 코드 복사·Worktree 생성과 다름 |
| Independent | 원본 대화 전부를 상속하지 않는 독립 컨텍스트에서 시작 |
| Shared Directory | 기존 동일 작업 디렉터리를 여러 세션이 사용할 수 있는 모드 |
| Git Worktree | 별도의 체크아웃과 브랜치 기반 작업 공간 |
| Handoff | 구현 사실·주요 선택의 WHY·검증·문제·참조를 간결하게 전달 |
| Verification | 실제 변경과 기존 계약·테스트 결과를 확인. 검증 범위를 명시 |
| Integration | 실제 Git 변경을 합치는 별도 행동. 사용자가 시점 통제 |

## 3. 핵심 사용자 흐름

1. 사용자가 Main과 설계·요구사항·하지 말아야 할 사항을 충분히 논의한다.
2. Main이 작업 범위·의존성·권장 실행 방식을 **제안**한다.
3. **사용자 선택 또는 명시적인 실행 지시가 있어야** 새 개발 세션을 생성한다.
4. 사용자는 각 세션에 대해 Context(Fork/Independent), Workspace(Shared/Worktree), 작업 순서·병렬성 및 실행 시점을 독립적으로 고른다.
5. Pi Compose가 기존 Pi·Git·tmux·선정된 도구를 이용해 준비·생성·연결하고, 세션 위치를 반환한다.
6. 개발 에이전트는 개발하며, 관련 에이전트에만 중요한 영향을 직접 공유한다.
7. 개발 완료는 명시적인 Handoff로 나타낸다. 이를 기점으로 기본 Git 검사를 실행한다.
8. 계약 영향·실패·불확실성이 있거나 사용자가 요청하면 **독립 컨텍스트에서** 심층 검증한다.
9. Main에는 다음 판단에 필요한 핵심 결론·WHY·근거 위치·한계만 전달한다.
10. 사용자가 원하는 시점에 코드 통합을 선택하고, 통합된 코드에서 필요한 검사를 수행한다.

이 흐름은 항상 모든 단계를 강제하는 절차가 아니다. 단순 작업은 단일 세션으로 충분할 수 있다.

## 4. 기능 요구사항

### P0 — 제품 정체성을 결정하는 필수 계약

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| **FR-01** | Main의 맥락을 보존하고 상세 도구 출력 유입을 최소화 | 탐색·테스트·Diff 분석을 독립적으로 수행하고 Main에는 간결한 결과가 남음 |
| **FR-02** | 작업별 Context를 **Fork / Independent** 중 선택 | 지정한 원본 세션을 분기하거나 새 독립 세션을 시작할 수 있음 |
| **FR-03** | Workspace를 **Shared Directory / Git Worktree** 중 선택 | 두 Context 모드와 두 Workspace 모드의 네 조합이 가능; 특정 조합 강제 없음 |
| **FR-04** | 작업 실행 시점과 순차·병렬 여부는 작업 특성·사용자 선택을 따름 | Main 제안이 있더라도 사용자 실행 선택 전 개발 세션을 만들지 않음 |
| **FR-05** | Pi·Git·tmux의 반복적인 준비 절차를 하나의 실행 경험으로 추상화 | Worktree 생성/재사용, 실행 cwd, Pi 생성·Fork, tmux 연결을 사용자가 매번 직접 조립하지 않음 |
| **FR-06** | 실행 대상 원본 세션을 정확히 지정 | 가장 최근 세션을 Main으로 무단 추정하지 않음; 선택한 원본과 실행된 Fork 관계 추적 가능 |
| **FR-07** | 실행 중 세션의 상태·전환·분할 관찰 | Dashboard에서 관련 Pi 세션을 찾고 직접 전환·관찰 가능; 확인 불가 상태는 임의로 성공 처리하지 않음 |
| **FR-08** | 계약의 이유·금지 강도·출처 보존 | “X 때문에 절대 Y 금지”가 “가능하면 Y 회피”로 바뀌지 않음; 원문이 필요할 때 출처 확인 가능 |
| **FR-09** | 개발 Agent의 간결한 Handoff | 무엇·왜·검증 내용·미해결 문제·실행/코드 위치를 포함; Handoff는 계약 승인이 아님 |
| **FR-10** | 상세 Diff·실제 코드 분석을 Main과 분리 | 검증 수행 세션이 Git 변경을 확인하고 Main은 의사결정에 필요한 결과와 참조만 받음 |
| **FR-11** | 중요한 영향만 관련 에이전트에 직접 공유 | 발견/제안/승인/구현 상태와 WHY를 구분; 모든 통신을 Main에 집중시키지 않음 |
| **FR-12** | 코드 통합 시점은 사용자가 선택 | 검증 완료만으로 병합·Worktree 삭제·세션 종료를 자동 실행하지 않음 |

### P1 — 처음부터 고려할 운영·안전 계약

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| **FR-13** | 작업 완료 신호와 실행 상태를 분리 | Pi Turn 종료, tmux Idle, 테스트 통과를 Handoff와 동일하게 취급하지 않음 |
| **FR-14** | Handoff 이후 기본 Git 검사 자동 실행 | 추적·미추적 파일, staged/unstaged, 기준 커밋과 검증 시점·범위를 확인 가능 |
| **FR-15** | 의미적 검증은 필요성에 비례해 수행 | 기본 검사와 심층 검증 구분; 불확실성·명시된 충돌·검사 실패·사용자 요청이 있을 때 독립 검증 가능 |
| **FR-16** | 세션 재개와 안전한 재시도 | 이미 있는 Pi 세션·Worktree를 우선 발견·재사용; 중복 실행·무단 삭제를 막음 |

| **FR-18** | 공통 실행 기능을 여러 진입점에서 재사용 | Pi 명령 및 명시적 자연어 요청에서 같은 실행 동작 사용; Dashboard 버튼 제공 가능 여부는 패키지 인터페이스 검증 |
| **FR-19** | 개별 작업 완료와 통합 완료 구분 | Git 병합 충돌 없음만으로 기능 완성을 주장하지 않음; 통합 후 필요한 검증 수행 |
| **FR-20** | 프로젝트 기존 계약 소스 존중 | 프로젝트의 AGENTS.md·명세·테스트를 재사용; 코드 관찰만으로 새 요구사항 생성하지 않음 |
| **FR-21** | **기본 Launch와 선택형 View를 독립적으로 사용** | 기본 Pi Package는 Launch만 자동 등록; Dashboard를 설치·활성화하지 않아도 Launch 사용 가능; 새 View는 Pi Extension·Package로 추가하며 기존 Launch 수정 불필요 |

### 세 가지 서로 독립적인 실행 선택

| Context | Workspace | 순서·병렬 | 허용 여부 |
| --- | --- | --- | --- |
| Fork | Shared Directory | 작업에 따라 선택 | 허용 |
| Fork | Git Worktree | 작업에 따라 선택 | 허용 |
| Independent | Shared Directory | 작업에 따라 선택 | 허용 |
| Independent | Git Worktree | 작업에 따라 선택 | 허용 |

Shared Directory에서 병렬 수정을 선택하면 물리적으로 변경이 섞일 수 있음을 안내한다. **불가하다는 이유로 자동으로 Worktree로 바꾸지 않는다.**

**목표 지표 후보**(숫자 목표는 미확정): 개발 세션 생성에 필요한 수동 단계 수, 중복 생성·실패 복구율, Main에 유입된 일시적 도구 결과 분량, 완료 후 누락된 계약 문제, 자동 기본 검사 비용. 기준 값 없이 임의의 성능 목표를 정하지 않는다.

## 6. 의사결정 경계

- **Agent가 스스로 해결:** 기존 계약 내 구현 선택, 명백한 오류 수정, 영향 없는 내부 변경, 필요한 동료에게 알림.
- **상호 협의:** 관련 에이전트의 전제나 인터페이스에 영향을 주는 변경.
- **사용자가 결정:** 사용자와 확정한 계약·중요한 제품 동작의 변경, 새로운 의사결정 권한이 필요한 경우, 실제 Git 통합 시점.
- **검증이 할 일:** 제안이나 주장에 의존하지 않고 코드·기준 커밋·원래 계약 출처를 확인.
- **금지:** 에이전트의 “사용자가 승인했다”는 전달 메시지를 직접 사용자 승인으로 승격.

## 7. 첫 구현의 수용 시나리오

1. Main을 명시적으로 지정하고 Fork + Worktree를 한 번의 요청으로 시작; Main은 유지되고 새 위치에 세션이 생성된다.
2. Fork + Shared, Independent + Worktree, Independent + Shared 세 조합도 같은 진입점에서 시작한다.
3. 대시보드에서 실행한 Pi 에이전트를 확인하고 전환한다. 없는 상태 정보는 “확인 불가”로 표현한다.
4. Pi 실행 실패 후 재요청 시 기존 Worktree를 감지하고 데이터 손실 없이 재시도한다.
5. 개발 Agent가 완료를 명시적으로 인계하면 기본 Git 검사를 수행하고, 상세 Diff 대신 참조·요약만 상위에 전달한다.
6. API 계약 관련 변경이 있으면 원래 “왜 금지했는지”를 확인해 독립 검증에서 우려를 보고한다.
7. 개별 테스트가 통과해도 통합된 코드에서 API/UI 불일치가 발견될 수 있음을 처리한다.
8. 통합 및 Worktree 삭제가 사용자 선택 없이 자동 실행되지 않는다.

## 8. 보류 및 출처

- **기술 미확정:** workmux / ccmux / pi-agent-hub의 채택, Dashboard 실행 옵션 통합, 통신 패키지, 실행 메타데이터의 저장 방식.
- **기술 검증 필요:** 실제 Pi 1.4.0과 workmux의 호환성, Worktree에서 정확한 세션 Fork 및 원래 계약의 보존, Shared Directory 세션 탐지, 인계 이벤트와 Git 검사의 연결.
- **완료 문서:** [TRD](TRD.md), [Architecture](ARCHITECTURE.md), [Implementation Plan](IMPLEMENTATION_PLAN.md)에서 이 사항들을 별도 관리한다.
