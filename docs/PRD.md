# PRD — Pi Compose

> 제품 결정 기준: 2026-11-10 · **정책 합의와 코드·실사용 검증은 별개**
>
> [비전](VISION.md)과 [사용자 문제](PROBLEM_STATEMENTS.md)는 이 문서의 선행 근거입니다. PRD는 채택한 제품 요구사항만 설명합니다.

## 1. 제품 원칙

- **Main 컨텍스트 보호:** 사실·선택 이유·강한 제약·미결정을 보존하며 실행 로그와 무관한 결과를 자동으로 쌓지 않습니다.
- **정확한 맥락 상속:** 맥락이 필요한 개발은 실제 Pi 활성 대화의 완료 지점을 별도 Work 세션으로 Fork합니다. Resume이나 모델 요약으로 대체하지 않습니다.
- **독립 작업:** 전체 맥락이 필요 없는 탐색·조사·테스트 실행은 Support에서 처리할 수 있습니다.
- **사람이 결정:** Agent의 제안·보고, 코드 변경, 테스트 실행, 사용자 승인, Main 정책 채택은 서로 다른 사건입니다.
- **기존 도구 우선:** Pi Extension·세션·TUI, Ghostty, Git을 재사용합니다. 자체 Agent 런타임·불필요한 관리 화면을 만들지 않습니다.

## 2. Agent와 세션

| 역할 | 주된 일 | 컨텍스트 |
| --- | --- | --- |
| Main | 문제·제품 정책·설계·결정과 이유, 다음 판단 | 원본 Pi 대화 |
| Work | 구현·수정·테스트 코드 작성 등 맥락이 필요한 작업 | 사용자가 선택한 Pi 완료 분기를 실제 Fork |
| Support | 탐색·자료 조사·테스트 실행·독립 검증 | 새 독립 Pi 세션 |

- `pic`은 현재 프로젝트에서 **새 Main**을 직접 엽니다. 별도 Overview를 거치지 않습니다. 기존 저장 세션 복원은 Pi 기본 기능을 사용하며 Work/Support를 임의로 Main으로 바꾸지 않습니다.
- 같은 프로젝트에 여러 Main을 둘 수 있습니다. Fork 원본의 세션·활성 분기, 새 Agent를 요청한 세션, 파일 작업 디렉터리는 각각 구분합니다.
- Main/Work/Support 어느 세션에서도 사용자의 명시적 지시로 Work나 Support를 만들 수 있습니다. Agent 자체의 자율 생성·자동 스케줄링은 현행 범위에 포함하지 않습니다.
- 원본 Pi JSONL은 Fork로 수정하지 않으며, 중단된 도구 호출을 완료 지점으로 잘못 취급하지 않습니다.

## 3. 작업 시작과 Git

| 입력 | 컨텍스트 | 파일 공간 |
| --- | --- | --- |
| `>w 작업` | 현재 Pi 완료 분기 Fork | 입력 Agent의 현재 디렉터리 공유 |
| `>w @세션 작업` | 같은 프로젝트에서 명시적으로 선택한 Pi 세션 Fork | 입력 Agent 디렉터리 공유 |
| `>>w 작업` | 현재 완료 분기 Fork | 입력 Agent의 Git HEAD 기반 새 Worktree |
| `>>w @세션 작업` | 선택한 세션 Fork | 입력 Agent의 Git HEAD 기반 새 Worktree |
| `>s 작업` | 독립 Support | 입력 Agent 디렉터리 공유 |
| `>>s 작업` | 독립 Support | 입력 Agent의 Git HEAD 기반 새 Worktree |

- 직접 위임은 Pi 입력 첫머리에서만 해석합니다. `>`는 디렉터리 공유, `>>`는 새로운 Worktree를 뜻합니다. 작업 지시가 없으면 Agent를 실행하지 않습니다.
- 새 Agent는 현재 Pi가 실행 중인 Ghostty Terminal을 기준으로 별도 Native Split에 엽니다. 기존 Agent의 프로세스·Pi 세션·포커스를 임의로 교체하지 않습니다.
- 미커밋 변경은 Worktree에 자동 복사하지 않습니다. Git 병합·Worktree 삭제·세션 삭제를 자동으로 실행하지 않습니다.
- 실패·취소·재개 과정에서 중복 실행 또는 최초 지시 자동 재전송을 추측해서는 안 됩니다.

## 4. Main 결정 변경 전파 — 2026-11-11 최신 사용자 결정

> **확정된 목표:** Main에서 사용자가 "B안으로 확정합니다"처럼 기존 제안을 명확히 승인하면 별도 등록 조작 없이 관련 Work에 변경을 전파합니다. Work는 원본 Pi Fork를 유지하며 전체 대화를 동기화하지 않습니다.

1. **권위:** 정책은 사용자 승인된 Main 결정만 유효합니다. Assistant 제안·Work 보고·실행 상태는 승인 정책이 아닙니다. 승인 발화와 실제 제안 원문을 연결하지 못하면 임의로 결정하지 않습니다.
2. **기준:** Pi 세션·활성 분기 계보와 승인 Entry ID가 결정의 정본 근거입니다. 로컬 변경 스냅샷은 Work의 빠른 조회 인덱스로만 사용합니다. 과거 분기로 돌아가면 해당 분기에서 유효한 결정 집합을 다시 계산합니다.
3. **구독:** Fork 원본과 요청자 관계를 구분하여 정책 소유 Main을 찾습니다. 복수 Main이 충돌할 때 프로젝트 이름만으로 단정하지 않습니다. 초기 자동 전파는 확정된 정책 소유 Main의 Work를 대상으로 합니다.
4. **효율:** 평범한 대화나 변경이 없는 실행에는 정책 추출/추가 모델 호출을 하지 않습니다. 승인 후보에 한해 기존 대화의 필요한 부분을 확인하고, Work는 변경분만 다음 모델 호출에 추가합니다.
5. **회복:** Work가 오프라인이거나 변경 이벤트를 놓쳐도 시작·재개·Handoff 경계에서 유효 결정 상태를 다시 조회합니다. 실시간 알림은 최적화일 뿐 정확성의 유일한 근거가 아닙니다.
6. **적용:** Work가 정책을 전달받은 것과 파일 수정·테스트·결정 반영은 다릅니다. Work는 작업 범위 안에서 자율 수정하고, 작업의 실질적 재정의가 필요하면 Main에 질문합니다. 명시적인 중단 지시도 이미 완료한 실행을 되돌렸다고 표현하지 않습니다.
   - **선택적 조회:** Work의 `?p`는 미검토 확정 정책을 자기 작업 맥락에서 즉시 검토하는 읽기 전용 요청입니다. 정상 자동 전파의 필수 단계가 아니며 변경이 없으면 모델 턴을 만들지 않습니다. Main의 미확정 승인 후보는 `/compose policy`에서 소유 Main만 처리합니다. `>`·`<`는 Agent 방향 의미를 유지합니다.
7. **자연어의 한계:** 모델이 승인 내용을 완벽히 해석했다고 가정하지 않습니다. 모호한 확정/원문 미확인은 전파하지 않고 상태를 드러냅니다. 자동 감지 누락률과 정확도는 별도 검증 대상입니다.

## 4.1 Work → Main Handoff (Work-owned reference)

- Work `<`에서 결과·필수 WHY/제약·검증·정책 최신성 상태를 포함한 **정확한 본문을 사용자에게 한 번 승인**받습니다. 승인 전 전송은 금지합니다.
- **자율성·협력성:** Main은 확정 정책의 권위와 이유·범위를, Work는 구현·검증·영향 판단과 Handoff 내용 품질을 소유합니다. 공유 계약으로만 협력하며 Main이 Work 내부 작업을 중복 의미 심사하지 않습니다.
- Main은 승인된 원본을 영속 보관하고 수신자·원본 Work/Fork 계보·해시·활성 분기·중복만 **기계적으로** 확인합니다. 정상 경로에서는 Work 구현/테스트나 Main 결정과의 의미 비교 모델을 호출하지 않습니다.
- 승인된 **동일한 Brief**를 출처가 명시된 참고 보고로 기록합니다. Pi receipt 전에는 완료 표시하지 않습니다. 별도 Main 승인·모델 턴·정책 자동 변경·Git 병합을 하지 않습니다.
- 제한된 WHY·미검증/미실행 테스트·정책 동기화 실패를 Work 보고에서 명확히 표기하면, 사용자 승인 후 그 상태 **그대로** 수신합니다. 불완전성을 작업 완료나 확정 정책으로 승격하지 않습니다.
- 잘못된 대상·분기·계보·본문은 자동 삽입하지 않고 영속 저장 상태로 보류합니다. 실제 사용자가 다른 분기에 명시적 반영을 선택하는 경우는 정상 자동 수신과 별도 예외 동작입니다.
- 과거 `compareHandoffWithMain`의 Claim 전체 재분류와 `insufficient` 자동 보류는 **이전 정책**이며 새 기본 경로에서 사용하지 않습니다.

**구현·검증 구분:** 위 문구는 채택한 제품 계약이며 Draft 작업 브랜치에 작성 중인 코드의 E2E 성공을 의미하지 않습니다. 정책 승인 추출·Work 실행 중 변경 감지·Pi 메시지 receipt를 실제 환경에서 검증해야 합니다.

## 5. 프로젝트 문서 관리

- 루트 `AGENTS.md`는 짧은 비전과 주요 코드/문서 위치만 제공합니다. 문서별 정본은 [문서 안내](README.md)에서 관리합니다.
- Main은 사용자의 **명확한 승인**을 확인한 중요한 정책·계약 변경을 해당 정본 문서에 반영합니다. Agent 제안과 미승인 보고는 정책이 아닙니다.
- Work는 실제 개발로 바뀐 구현 설명·기술 사용법을 수정할 수 있지만, **제품 정책·핵심 도메인 계약·중요 기술 결정의 승격/변경을 독자적으로 수행하지 않습니다.** 그런 발견은 Main에 전달해 검토합니다.
- 새 문서 생성은 사용자가 요청하거나 명시적으로 승인한 경우에만 수행합니다. 별도 문서·ADR·DB를 자동으로 늘리거나 같은 계약을 여러 문서에 복제하지 않습니다. 프로젝트 문서 변경과 Pi 대화 롤백은 별개의 작업입니다.

## 6. 비목표

Sidebar·Overview·Summary Overlay, Orca, tmux/workmux, 별도 GUI/상주 서버/메시지 브로커, 자동 멀티 Agent 스케줄링, 자동 정책 승인·Git 병합·세션/Worktree 삭제는 현재 목표가 아닙니다.

## 7. 미해결 검증과 완료 기준

- **자동 자연어 감지:** 명확한 승인 구문에서 사용자의 실제 결정과 원래 대안을 연결합니다. 확정되지 않은 제안·부정·다른 Main의 결정이 전파되지 않는지, 명시적 승인도 놓치지 않는지 실제 사례로 검증해야 합니다.
- **정확한 적용 범위:** 기본 정책 소유 Main의 Work만 구독합니다. 여러 Main·Work에서 출처가 충돌하는 경우 조용히 대상 Main을 추측하지 않습니다.
- **Work 처리 상태:** 새 결정이 모델에 노출·세션에 기록·실제 구현에 반영된 사건을 구분해야 합니다. 전달만으로 실행 완료 상태를 표시하지 않습니다.
- **장기 맥락:** Compaction/ContextEdit·세션 재개 후에도 활성 분기의 결정 원본과 WHY가 부정확하게 소실되지 않아야 합니다.
- **실사용 검증:** 새 Main, 정확한 Fork, Worktree, 실행 중 변경, 미검증 결과의 Handoff, 분기 전환, 중복, 오프라인 복구, Pi 메시지 receipt, macOS/Ghostty의 실제 동작을 확인해야 합니다.
- **비용:** 변경 없는 일반 실행에 정책 판단용 모델 호출이 발생하지 않아야 하며, 승인 감지로 인한 추가 호출·토큰·지연과 줄어든 재작업을 비교해야 합니다.
